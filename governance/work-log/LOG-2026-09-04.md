### REQ-SEC-002 — staged fix, part 1: `students` + `admin_users` locked down
Before touching anything, surveyed actual usage to size the real fix:
- `pg_tables` confirmed RLS is disabled (`rowsecurity = false`) on every
  table in `public` except `impersonation_audit_log`/`impersonation_codes`.
  This resolves the open question left by the 2026-08-21 audit ("couldn't
  determine whether RLS is disabled or an old permissive policy is active
  underneath") — it's neither; RLS was simply never turned on for anything
  else.
- Both the mobile app **and** the admin-panel talk to Postgres with the
  public anon key directly (`admin-panel/src/lib/supabase.js` uses
  `NEXT_PUBLIC_SUPABASE_ANON_KEY`, no service role) — confirmed `anon` held
  full SELECT/INSERT/UPDATE/DELETE grants on `students`, `employees`, and
  `admin_users`.
- `supabase_service.dart` has ~85 direct `.from('table')` calls (vs. 2 RPC
  calls outside login), so naively enabling RLS with an `auth.uid()`-based
  policy would lock out the mobile app entirely, not just close the hole —
  the mobile app never creates a real Supabase Auth session (custom RPC
  login instead). This is why TODO.md already flagged REQ-SEC-002 as a
  MAJOR/architecture-level change.
- Found a stale/wrong comment in `mobile-app/SUPABASE_BIRTHDAYS.sql` — it
  claims `students`/`employees` already have owner-based RLS. They didn't;
  a `students_own_profile` policy did exist on `students` (inert while RLS
  was off) but nothing on `employees`.
- Admin-panel **does** use real Supabase Auth (`supabase.auth.signInWithPassword`
  in `login/page.js`), so `auth.uid()` is meaningful there — this made
  `students` and `admin_users` safe to lock down immediately, since neither
  is touched by the mobile app's anon-key calls.
- `employees` was **deliberately excluded** from this pass — the mobile app
  reads/writes it directly with the anon key for the teacher's own profile
  (3 call sites: fetch own profile, update own profile), with no real
  session. Locking it now would break the teacher app immediately. Deferred
  to be fixed together with REQ-SEC-004 (which already needs the same
  RPC-wrapping + app rebuild).

Presented this scope/tradeoff to the user before writing any SQL (per this
project's "plan first" rule for security/DB changes) and got explicit
go-ahead for the staged (PII-first) approach.

**Applied via `mcp__supabase__apply_migration`** (`lock_down_students_admin_users_rls`):
- Added `public.is_admin_user()` — `SECURITY DEFINER` helper checking
  `EXISTS (SELECT 1 FROM admin_users WHERE id = auth.uid())` — used to avoid
  RLS self-recursion on `admin_users`.
- `REVOKE ALL ... FROM anon` on both `students` and `admin_users`.
- Enabled RLS on both tables.
- `students`: one `FOR ALL TO authenticated` policy gated on
  `is_admin_user()`.
- `admin_users`: SELECT policy allows `auth.uid() = id` (self, needed by the
  login/set-password flows) OR `is_admin_user()`; separate INSERT/UPDATE/
  DELETE policies all gated on `is_admin_user()`.

**Verified live**, same method as the original 2026-08-21 audit — an
unauthenticated REST call with the real public anon key:
```
GET /rest/v1/students     -> 42501 permission denied for table students
GET /rest/v1/admin_users  -> 42501 permission denied for table admin_users
```
Both now correctly refuse anonymous access. Also confirmed the pre-existing
`students_own_profile` policy (`app_user_id = auth.uid()`) is harmless —
correct condition, and moot anyway since `anon` no longer has table-level
grants at all.

**One accepted side effect:** admin-panel's login page shows a pre-login
student/employee headcount stat (`login/page.js:49-50`) via an anonymous
read — the student count will now come back null. It already has a
`.catch(() => {})` fallback to "—", so it degrades gracefully; not treated
as a regression worth blocking on.

**Correction to the reasoning above:** the "3 direct `employees` call sites"
cited as the reason to defer `employees` are `fetchFaceEmbedding`/
`saveFaceEmbedding`/`fetchAllFaceEmbeddings` (`supabase_service.dart:159-193`)
— the attendance-kiosk face-recognition flow, which by necessity runs before

**not** the teacher's own-profile view/edit, which already goes through
`teacher_login` (initial fetch) and the `teacher_update_profile` RPC below —
both already SECURITY DEFINER. The conclusion (defer `employees`) still
holds, but for the kiosk reason, not a profile-fetch reason.

### REQ-SEC-004 — `teacher_update_profile` now requires the current password
Read the RPC (`mobile-app/SUPABASE_TEACHER_SETTINGS.sql`), its Dart caller
(`supabase_service.dart:758-765`), and the calling UI
(`teacher_profile_page.dart` `_openEditProfile`). Confirmed the RPC took
`p_employee_id/p_name/p_phone/p_email` with no password check at all —
unlike its sibling `teacher_change_password`, which verifies
`app_password` first.

**Applied via `mcp__supabase__apply_migration`**
(`teacher_update_profile_require_password`):
- `DROP FUNCTION IF EXISTS teacher_update_profile(TEXT, TEXT, TEXT, TEXT)` —
  explicit, because `CREATE OR REPLACE` with a different parameter list
  creates a second overload rather than replacing the old one; skipping the
  drop would have left the no-password version callable forever alongside
  the new one, silently defeating the fix.
- Recreated `teacher_update_profile` with a 5th required `p_password`
  param, checked the same way `teacher_change_password` checks
  `p_old_password` — returns `NULL` (same "didn't work" signal the caller
  already handles) on either a bad employee id or a wrong password.
- Re-granted `EXECUTE` on the new 5-arg signature to `anon`.

**Verified live** via direct SQL calls (no real employee touched — used a
nonexistent id + an obviously wrong password, so the check fails before any
`UPDATE` runs):
```
select teacher_update_profile('00000000-...','x','x','x','wrong-pw');
  -> null
select teacher_update_profile('00000000-...','x','x','x');   -- old 4-arg
  -> ERROR: function teacher_update_profile(unknown,unknown,unknown,unknown)
     does not exist
```
Confirms the insecure path is gone, not just shadowed by an overload.

**App side** (`mobile-app`):
- `supabase_service.dart` — `updateTeacherProfile` now takes a required
  `password` and passes `p_password` through.
- `teacher_profile_page.dart` — Edit Profile sheet gained a required
  "Current Password" field (obscured, with a show/hide toggle, matching the
  existing Change Password sheet's style); save handler now validates it's
  non-empty and shows "Incorrect password. Please try again." when the RPC
  returns `null`.
- `flutter analyze` on both touched files: clean, only pre-existing
  style/deprecation infos (`withOpacity`, missing `const`), no errors.
- **Not visually tested on a real device** — BlueStacks wasn't running when

  change); this is a real behavior change to a screen every teacher uses, so

    even though `student.fees.total` (the real snapshot) was sitting right

### REQ-BUG-003 — Fee payment save no longer resets the reminder selection
Confirmed root cause: `fees\page.js`'s "init reminder selection" effect
fired on every `students`/`feesMap` change and fully re-derived
`selectedIncomplete` from scratch as "every currently incomplete student" -
including the reload that happens right after `handleSavePayment`/
`handleSaveInventory` succeed, silently discarding any manual unchecks.

**Fix:** added a `reminderInitYear` ref tracking which academic year the
selection was last initialized for.
- Year actually changes (or first load) → full re-select, as before.
- Any other reload (e.g. after saving a payment) → prune the *existing*
  selection down to just the students still incomplete, instead of
  resetting it. This preserves deliberate unchecks while still correctly
  dropping anyone who just got fully paid off - a simpler version of this
  fix (just skip the effect entirely after first init) would have left
  paid-off students' enrollment numbers stuck in the Set forever, inflating
  the "N selected" / "sent to N students" counts, so the prune step is
  load-bearing, not just defensive.

`next lint` on `fees/page.js`: clean. Not click-tested (would need the
admin-panel dev server running).

### REQ-BUG-004 — Mark Attendance race condition confirmed and fixed
TODO.md flagged this as "PLAUSIBLE, not confirmed" — read `loadAttendance`
(`attendance\page.js:123-146`) closely to check whether the gap was real,
not just theoretical. It is: the function has zero request-ordering guard,
and is re-triggered via `useEffect` on every `selectedClass`/`selectedDate`
change. If an admin switches class before the previous class's fetch
resolves, whichever response lands last wins - regardless of which one is
actually stale - and a Save right after would persist that wrong data
against the *currently selected* (correct) class/date, since `handleSave`
reads `selectedClass`/`selectedDate` fresh but `statusMap` from whatever
last got written.

**Fix:** added a `loadReqId` ref, incremented at the start of every
`loadAttendance()` call. The response handler, catch block, and finally
block all check `reqId === loadReqId.current` before touching
`statusMap`/`wasMarked`/`editMode`/`attLoading` - a response that's no
longer the latest request is silently discarded instead of applied.

Confirmed via code reading, not a live reproduction (would need the
admin-panel dev server running + deliberately racing two fetches, which
isn't practical to script safely against production Supabase data this
session). `next lint` on `attendance/page.js`: clean.

### REQ-BUG-007 — Homework no longer shows "Overdue" on its own due date
Confirmed TODO's description: `student_homework_page.dart` already has a
correct, date-only `_isPastDue()` used for the Active/Archive tab split,
but its itemBuilder separately recomputed `overdue` inline by comparing
`due` (parsed at midnight) against `DateTime.now()` (full timestamp) - true
from midnight onward on the due date itself, contradicting the tab it's
sitting in. `teacher_homework_page.dart` had the identical pattern with no
existing correct helper to point to.

**Fix:**
- `student_homework_page.dart` — itemBuilder now calls `_isPastDue(hw)`
  instead of duplicating (incorrectly) the same check.
- `teacher_homework_page.dart` — no reusable helper existed here, so both
  `overdue` and `urgent` now compare against `today` truncated to midnight
  first, same fix shape as the student side. This also fixes the
  side-effect TODO named: the due date itself is now correctly `0` days
  away, so it gets the amber "urgent" treatment instead of never reaching
  it (since `overdue` was wrongly true first).

`flutter analyze` on both files: clean, only pre-existing infos.
