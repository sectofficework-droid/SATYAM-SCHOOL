Two things, back to back in the same session: delete two leftover QA test

management/senior admin) to log into any student's or teacher's mobile app

## What I did

### 1. Deleted the QA test accounts
You asked me to remove the standing `ADMIN TESTSTUDENT`/`ADMIN TESTSTAFF`
test logins we'd set up a few days ago. I checked the database first to
make sure those were the only test-like accounts (they were), confirmed
with you since deleting from production is permanent, then deleted both
cleanly — no other tables were pointing at them, so nothing else needed
cleaning up. Verified they're gone.

### 2. Built the "Admin Access Code" feature
You wanted full account access to any student/teacher for QA/testing,
without needing their real password. I looked into how login actually
works first — turns out the mobile app doesn't use a real login-session
system at all (it's a simple check against the database that just hands
back the person's profile), so instead of anything fancy, I designed a
one-time code system: you generate a short code from the admin panel for
whichever student or teacher you need to check, and typing that code into
the mobile app's login screen logs straight into their account — the app
treats it exactly like a normal login.

I wrote up a plan first (this is a real access-control feature, worth
getting your sign-off before coding), asked you three quick questions
about how it should work, and you picked the recommended option each time:
- Code gets typed into the app itself (not a special link).
- Only you and other senior admins can generate codes — regular admins
  can't.
- Codes expire in 10 minutes and can only be used once. After that, it's a
  totally normal session — no special warning banner in the app, but every
  code generated and every use (successful or not) gets written down in a
  permanent log so there's always a record of who accessed what.

Then I built it: new database tables and functions, a "Generate Code"
button on both the student and teacher detail pages in the admin panel
(only visible to you/senior admins), a new "Access Codes" tab in Settings
showing the full history, and a new option on the mobile app's login screen
("Have an Admin Access Code?").

**I found and fixed a real security bug in my own work before finishing.**
After building the database side, I tested it properly — and found that
because of a default Postgres behavior I hadn't accounted for, two of the
internal helper functions were reachable by literally anyone with your
app's public key, no code or login needed at all, and would hand back a
student's or teacher's full profile. I confirmed this was real (pulled a
real teacher's info to prove it), then fixed it immediately with a second
database update that locks those functions down properly. Re-tested
afterward to confirm the leak is closed and the real feature still works.

Both database changes had to be run through the Supabase dashboard
directly (same as password-hashing fix from last week) — I can't run
schema changes like new tables/functions through the app's API key alone,
only actual data changes. I opened the right page for you both times and
you pasted and ran them.

## Decisions
- Built a one-time-code system instead of anything more complex, since the
  mobile app has no real login-session to plug into anyway — this turned
  out to be simpler and just as secure.
- Restricted code generation to management/senior admin only, matching how
  other sensitive actions (like permanent delete) are already locked down
  in your admin panel.
- Fixed the security bug I found myself, same session, rather than leaving
  it for later — it was a real live exposure, not a hypothetical one.
- Didn't touch anyone's real password anywhere in this feature — it's
  purely a separate, audited side door, not a password reset.
