# LOG-2026-09-19 — Admin role-tier enforcement (REQ-SEC-005)

## What I set out to do

While closing out a question from the Staff App Unification plan (does
per-role permission behavior in the admin panel really live only in
client-side Zustand state, as an older doc claimed?), I found the real
answer was worse than the question assumed — and you asked me to fix it
properly.

## What I found

There's no Zustand permissions matrix in the code at all — that doc line
was stale. What actually exists is a handful of `authUser.role !==
"normal_admin"` checks scattered across different pages, each one only
controlling whether a button is *shown*. The database mostly didn't know or
care which tier of admin was making a request, only that they were *an*
admin.

The worst instance: any logged-in admin, including the lowest tier
(`normal_admin`), could open browser devtools and call the Supabase client
directly to set their own account's role to `management` — the highest
tier. Nothing on the server side stopped it. The same gap let a
`normal_admin` permanently delete a student record or flip the
diagnostic-logging switch, both features the interface reserves for higher
tiers.

## What I did

You asked me to prepare fully, ask everything I needed up front, and then
run the whole fix through to a production-ready state without stopping to
check in again. I asked four rounds of clarifying questions first (scope,
whether to apply the database fix directly, whether to commit/deploy the
code, and how to handle a sequencing conflict between two of your answers),
then executed without further interruption:

**1. Wrote and applied a migration directly to production.** Five new
database functions (`admin_has_role`, `admin_create_user`,
`admin_update_user`, `admin_delete_user`,
`admin_delete_student_permanently`) now check the caller's real role before
allowing anything — matching the one place this project already did this
correctly (the admin impersonation feature). Per your decisions: only
`management` can create, edit, or promote someone to `senior_admin` or
`management`; `senior_admin` can only manage `normal_admin` accounts; and
nobody — at any tier — can change their own role or delete their own
account. I then revoked the old direct-write permissions on the two
affected tables so these new functions are the only way in.

**2. Found and fixed a smaller version of the same bug before it ever
shipped.** The diagnostic-logging toggle table doesn't exist in production
yet (its own migration was written weeks ago but never run). I fixed that
pending file's policy in place, so when it does eventually get applied, it
won't carry the same flaw.

**3. Found and fixed something the database's own security checker
flagged.** Right after applying the migration, Supabase's built-in security
advisor pointed out that my 5 new functions were technically callable by
anonymous, logged-out visitors too — a side effect of how Postgres grants
function permissions by default. The functions would have rejected an
anonymous caller anyway (they check for a real logged-in admin first), but
I closed that door explicitly rather than relying on the fallback.

**4. Verified all of it against real data, safely.** Rather than needing
actual login passwords for a `normal_admin`, `senior_admin`, and
`management` account, I simulated each one directly in the database (a
standard technique for testing this kind of permission logic) and ran 16
test cases — every "this should be blocked" and "this should still work"
scenario — all inside a transaction I rolled back afterward, so nothing was
actually changed. All 16 passed. I did catch one mistake of my own along
the way: an early combined test run made it look like three checks were
failing, but that turned out to be my test contaminating itself (an earlier
step in the same test had already promoted the account I was testing with),
not a real problem with the fix. I re-ran those three in isolation to
confirm.

**5. Updated the admin panel's code** to call these new, safer functions
instead of writing to the tables directly — three calls in the Users &
Roles screen, and the student permanent-delete function.

## What's left, on purpose

Per your instructions, you chose to apply the database fix immediately
rather than wait — which means, until you deploy this staged code,
"Settings → Users & Roles" (adding/editing/removing admin accounts) and
"permanently delete a student" will show an error in the live admin panel
for everyone, including management. That was a deliberate tradeoff you
made: close the security hole now, accept the short inconvenience until you
deploy. The code is staged, not committed — you said you'd rather commit
and push it yourself when you're ready.

Two things came up that I did **not** touch, on purpose:

- The "create a new admin account" feature turns out to have never fully
  worked, even before today — it's missing a step (linking to a real login
  account) that was already an open item on your roadmap. My fix doesn't
  make this better or worse; I just confirmed it during testing.
- A very similar version of this same problem exists in the SEF
  organization's salary/employee screens. I flagged it but didn't start
  fixing it — it needs its own look first, and you asked me to keep this
  session scoped to just the admin_users/student-delete/diagnostics issue.

## Later the same day again: you asked me to check on everything pending, then work through REQ-SEC-002

**You asked what was still pending, so I checked the whole TODO list against
live reality** rather than trusting the file — found a few notes had gone
stale (a table count, a feature's actual status) and fixed them, but also
found something that couldn't wait.

**A fix from earlier today had broken something live.** The batch that
locked down 46 tables this morning had wrongly grouped `tasks` and
`daily_task_targets` in with the safe, admin-only ones. They weren't — the
Teacher app's "My Tasks" and "Daily Tasks" screens both need to read
through them as part of a different query, even though nothing calls them
by name directly. Every teacher opening either screen had been getting a
silent failure since that fix went out this morning. I caught it, restored
just the narrow read access those two screens actually need, and verified
the fix didn't reopen anything else.

**Then you asked me to review the plan for the rest of the table exposure,
and I found one more small gap in my own earlier work** — a table
(`daily_tasks`) had been dropped from the plan by mistake. Fixed the plan,
then applied the next two safe batches from it (16 more tables) the same
way as this morning's fix. Verified: the count of still-exposed tables
dropped from 33 to 17, and the ones left are exactly the hard cases the
plan already knew needed more care — no surprises.

**While tracing those hard cases, found something more serious: every
enrolled staff member's actual face-recognition data was sitting
completely open on the internet.** Not a name or a phone number — the raw
biometric measurements the kiosk uses to recognize someone's face. Anyone
with the same public key the app itself uses could have downloaded all of
it, no login of any kind. You told me to treat this like the urgent
password-backup issue from this morning and fix it right away rather than
wait for the bigger piece of work it was found inside of. I built a
narrower, separate safety check for just this one piece (a short-lived
pass generated when someone enters the correct kiosk PIN, checked again on
each biometric read/write) and closed off the direct access entirely. I
made a mistake on the first attempt — the way I tried to lock down that
one piece of data quietly didn't actually work, and a direct test proved
it — so I fixed that properly (verified this time) before moving on. This
one needs a new version of the attendance-kiosk app installed on the
physical device before it's actually protected there; I built it, but
haven't been able to test it against the real kiosk PIN myself.

**Then you asked me to actually build the bigger fix, not just plan it.**
The core problem behind the last several tables is that the teacher and
student apps never really "log in" the way a website does — every request
looks identical to the database, whether it's really that person or not.
I asked you to choose between two real options: teach the apps to log in
properly (a bigger change you'd already ruled out elsewhere), or give each
login a temporary pass that gets re-checked on every sensitive action
(reusing a pattern already proven elsewhere in this project). You chose
the pass. I then asked how long a pass should last before needing a fresh
login, and you chose a week, refreshing itself as long as someone's
actively using the app.

**Given how large the full fix was, I asked how much to build right now,
and you chose the foundation plus the easiest third of it.** I built the
pass system itself (issued at login, checked and renewed on every gated
request) and wired it into every way someone ends up logged in — including
two paths I hadn't originally planned for (being logged in as someone else
via an admin-issued code, and switching between sibling accounts), since
those would have silently produced a broken, pass-less login otherwise. I
made one real mistake building this — a small coding error that would have
crashed the very first real check — caught it on the first test and fixed
it before continuing. Then I moved 9 of the remaining exposed tables
(leave requests, staff queries, in-app alerts, task assignments, daily
task checkoffs, attendance-correction requests, syllabus-edit requests,
and teacher-uploaded documents) behind that same pass system, closing two
smaller gaps along the way where a delete/close action had no ownership
check at all before today. Verified all of it works end to end without a
real login (simulated safely, rolled back afterward) and that nothing
outside these 9 tables was touched. Both the teacher and student apps
still build cleanly with all these changes in.

**What's left, on purpose:** three new debug versions of the app (kiosk,
teacher, student) are built but I haven't been able to install and test
any of them on a real device or with real login credentials — that's the
most useful next step. The remaining, harder third of the table-exposure
work (roughly 8 more tables, including exam marks and attendance, which
need a "is this teacher actually assigned to this class" check rather
than a simple ownership check) is planned but not started — deliberately,
given how much ground this session already covered. Password-change was
also deliberately left out of the new pass system for now, flagged rather
than silently skipped, since doing it safely needs its own careful pass so
someone doesn't accidentally lock themselves out the moment they change
their password.

## Later the same day, yet again: you asked me to code-review today's Cat3 changes

**You asked me to run a review over today's diff**, so I ran it through
`ocr delegate` (this project's code-review CLI, in host-agent delegation
mode — it hands me the diff and rules directly rather than needing its

**Found one real problem worth blocking on before device testing:
pre-existing logged-in sessions silently break once this ships.**
`AuthService.sessionToken` reads a `session_token` key that only exists
on profiles cached *after* today's login change — anyone who was already
logged in keeps `isLoggedIn = true` with no token, and nothing detects or
repairs that. Two of the newly added guards (`student_home.dart`,
`teacher_home.dart`) gate their *entire* notification load on that token
being present, not just the specific calls that actually need it — so a
pre-existing user opens Home to a blank, stale feed with no error at all.
The same guard pattern was applied to roughly 10 pages this session, so
the same silent breakage is likely repeated across most of them. Logged
as **REQ-BUG-015**.

**Found a second, smaller pattern: three submit flows fail silently
instead of showing an error.** `student_query_page.dart`,
`teacher_query_page.dart`, and `teacher_leave_page.dart` all return early
on a missing session token with zero user feedback — unlike
`teacher_question_bank_page.dart`, which already shows a proper "Session
error - please sign in again." message for the same condition. Logged as
**REQ-BUG-016**.

**Found one minor inconsistency**: `staff_enroll_list_page.dart` casts
`Get.arguments` straight to `String` with no fallback, unlike every other
call site touched today, which would throw instead of degrading if the
route were ever entered without valid arguments. Logged as **REQ-BUG-017**.

**Cross-checked the new SQL against the Dart call sites** — no RPC
signature mismatches found; the migrations from earlier today
(`SUPABASE_CAT3_FOUNDATION_MOBILE_SESSIONS.sql`,
`SUPABASE_CAT3_GROUP_A_RPCS.sql`,
`SUPABASE_FIX_FACE_EMBEDDING_EXPOSURE.sql`) line up correctly with how
the Dart side calls them.

**Nothing fixed yet** — this was a review pass only, at your request, and
all three findings came from reading the code, not from reproducing them
live. REQ-BUG-015 is the one to prioritize: it's exactly the kind of
thing the pending "not yet tested on a real device with a real login"
step for REQ-SEC-002 Cat3 would surface, so it's worth fixing before that
test rather than after.
