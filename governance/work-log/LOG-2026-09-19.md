# LOG-2026-09-19 — Admin role-tier enforcement (REQ-SEC-005)

## What I set out to do

While closing out a question from the Staff App Unification plan (does
per-role permission behavior in the admin panel really live only in
client-side Zustand state, as an older doc claimed?), I found the real
answer was worse than the question assumed — and you asked me to fix it
properly.

## What I found

There's no Zustand permissions matrix in the code at all — that doc line
was stale. What actually exists is a handful of `authUser.role !==
"normal_admin"` checks scattered across different pages, each one only
controlling whether a button is *shown*. The database mostly didn't know or
care which tier of admin was making a request, only that they were *an*
admin.

The worst instance: any logged-in admin, including the lowest tier
(`normal_admin`), could open browser devtools and call the Supabase client
directly to set their own account's role to `management` — the highest
tier. Nothing on the server side stopped it. The same gap let a
`normal_admin` permanently delete a student record or flip the
diagnostic-logging switch, both features the interface reserves for higher
tiers.

## What I did

You asked me to prepare fully, ask everything I needed up front, and then
run the whole fix through to a production-ready state without stopping to
check in again. I asked four rounds of clarifying questions first (scope,
whether to apply the database fix directly, whether to commit/deploy the
code, and how to handle a sequencing conflict between two of your answers),
then executed without further interruption:

**1. Wrote and applied a migration directly to production.** Five new
database functions (`admin_has_role`, `admin_create_user`,
`admin_update_user`, `admin_delete_user`,
`admin_delete_student_permanently`) now check the caller's real role before
allowing anything — matching the one place this project already did this
correctly (the admin impersonation feature). Per your decisions: only
`management` can create, edit, or promote someone to `senior_admin` or
`management`; `senior_admin` can only manage `normal_admin` accounts; and
nobody — at any tier — can change their own role or delete their own
account. I then revoked the old direct-write permissions on the two
affected tables so these new functions are the only way in.

**2. Found and fixed a smaller version of the same bug before it ever
shipped.** The diagnostic-logging toggle table doesn't exist in production
yet (its own migration was written weeks ago but never run). I fixed that
pending file's policy in place, so when it does eventually get applied, it
won't carry the same flaw.

**3. Found and fixed something the database's own security checker
flagged.** Right after applying the migration, Supabase's built-in security
advisor pointed out that my 5 new functions were technically callable by
anonymous, logged-out visitors too — a side effect of how Postgres grants
function permissions by default. The functions would have rejected an
anonymous caller anyway (they check for a real logged-in admin first), but
I closed that door explicitly rather than relying on the fallback.

**4. Verified all of it against real data, safely.** Rather than needing
actual login passwords for a `normal_admin`, `senior_admin`, and
`management` account, I simulated each one directly in the database (a
standard technique for testing this kind of permission logic) and ran 16
test cases — every "this should be blocked" and "this should still work"
scenario — all inside a transaction I rolled back afterward, so nothing was
actually changed. All 16 passed. I did catch one mistake of my own along
the way: an early combined test run made it look like three checks were
failing, but that turned out to be my test contaminating itself (an earlier
step in the same test had already promoted the account I was testing with),
not a real problem with the fix. I re-ran those three in isolation to
confirm.

**5. Updated the admin panel's code** to call these new, safer functions
instead of writing to the tables directly — three calls in the Users &
Roles screen, and the student permanent-delete function.

## What's left, on purpose

Per your instructions, you chose to apply the database fix immediately
rather than wait — which means, until you deploy this staged code,
"Settings → Users & Roles" (adding/editing/removing admin accounts) and
"permanently delete a student" will show an error in the live admin panel
for everyone, including management. That was a deliberate tradeoff you
made: close the security hole now, accept the short inconvenience until you
deploy. The code is staged, not committed — you said you'd rather commit
and push it yourself when you're ready.

Two things came up that I did **not** touch, on purpose:

- The "create a new admin account" feature turns out to have never fully
  worked, even before today — it's missing a step (linking to a real login
  account) that was already an open item on your roadmap. My fix doesn't
  make this better or worse; I just confirmed it during testing.
- A very similar version of this same problem exists in the SEF
  organization's salary/employee screens. I flagged it but didn't start
  fixing it — it needs its own look first, and you asked me to keep this
  session scoped to just the admin_users/student-delete/diagnostics issue.

**REQ-SEC-002 (the ~72-table exposure): now more precisely mapped.** It's
grown to 76 tables since it was last counted (this project has a
documented pattern of live/tracked-file drift, and this confirms it's
ongoing). Sorted them by real risk — financial data, personal documents,
exam integrity, general academic data, low-risk operational — and checked
which ones the mobile apps actually touch directly versus which are
admin-panel-only.

**Then you said to fix whatever was possible before starting new feature
work, so I did the safe half.** Before touching anything, I re-checked the
"mobile-touched" list myself by directly searching the mobile app's code,
rather than trusting the earlier check's list as-is — and found two real

project's mobile apps never create one (a known fact about this codebase
already recorded elsewhere), so those rules would have silently locked
every teacher and student out of homework, exams, marks, and attendance

after.

With that corrected, I fixed the **46 tables the mobile apps never touch

29, and every one of those 29 is a genuine mobile-touched table I'd
already identified, not a mistake. Also ran real before/after checks: an
admin can still read everything they could before, an anonymous visitor
now gets rejected, and the student-delete feature from earlier today still
works correctly now that two more of its tables are locked down too.

**The remaining 29 tables are not fixed, on purpose.** Each one needs its
exact usage pattern checked individually before I can write a safe rule
for it — rushing that risks breaking a live feature for an actual teacher
or student, and this project has no automated tests to catch a mistake
before someone notices by hitting it themselves. That's real work for its
own session, not something to force into this one.
