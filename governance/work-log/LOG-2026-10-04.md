## S3 / app_versions — found two real bugs, fixed both, hit a third issue that's a genuine blocker

User asked "why do you want to upload the apk" when I tried driving Chrome
to the raw AWS S3 console and hit an IAM sign-in wall - good challenge,
answered it, and it surfaced a much better path: Settings -> App Update
already exists in the admin panel for exactly this (presigned upload,
publishes the `app_versions` row), using server-side AWS credentials
neither of us has to touch directly.

**Bug 1 (real, confirmed): `publishAppVersion()` never set `app_versions.app`.**
That column is `NOT NULL` with no default - every publish attempt via this
UI has always failed outright, which is why `app_versions` has been
completely empty since the feature was built (not "unused", "unusable").
The form also had no selector for which app (Teacher/Student/Attendance
Kiosk) an APK belongs to. Fixed: added an app selector - confirmed the
correct values by reading `main_attendance.dart` rather than assuming from
the Gradle flavor name (`UserRole.kiosk`, not `'attendance'`) - threaded
through `getAppVersionHistory`/`getLatestAppVersion`/`publishAppVersion`,
and flavor-prefixed the S3 key since `pubspec.yaml`'s version number is
shared across all three flavors. Committed `712b229`, deployed, verified
live in the browser: selector renders correctly, defaults to Teacher App,
version code correctly computes from (empty) history.

**Bug 2 (real, confirmed): S3 CORS preflight 403.** Filled the form, user
selected the APK, clicked Publish - "Failed to fetch". Live-traced via
Chrome's network panel (not guessed) to an `OPTIONS` preflight to the S3
bucket returning 403. Found `uploadFileToS3Presigned` has exactly one
caller (this feature) - strong evidence this direct-browser-to-S3 path was
never actually exercised end-to-end before. Hypothesis: AWS SDK v3's
default `requestChecksumCalculation: WHEN_SUPPORTED` attaches
`x-amz-checksum-*`/`x-amz-sdk-checksum-algorithm` headers to the presigned
URL, which the bucket's CORS `AllowedHeaders` (configured before this SDK
default existed) doesn't list. Fixed via one-line client config
(`WHEN_REQUIRED` instead), committed `f6e3a5e`, deployed.

**Retried after the fix - partially confirmed, not fully fixed.** Re-checked
network traffic: the checksum headers are confirmed gone from the request.
But the preflight **still returns 403**. So Bug 2's fix was real and
necessary but not sufficient - the bucket's CORS policy itself doesn't
allow PUT from the admin panel's origin at all, independent of headers.
This needs an actual CORS rule added via AWS Console, which neither of us
can do without the user's own AWS login (same boundary as the raw-S3-
console attempt earlier - I won't enter AWS credentials myself). Gave the
user the exact CORS JSON to add. **User said "keep it in to do, will work
later" - explicitly deferred**, filed as `planning\TODO.md` REQ-BUG-060.

# Official Exams default full marks: 100 → 50

## What I set out to do
User asked how to update an official exam's full marks, then asked to change
the default from 100 to 50.

## What I did
In `admin-panel/src/app/(dashboard)/settings/ExamsTab.js`: changed the
"Add New Exam" form's default Full Marks value, its post-add reset value,
and the per-subject display fallback (shown when a subject has no saved
config yet) from 100 to 50. This only affects exams created from now on and
the display fallback - it does not touch already-saved marks.

User then explicitly asked to also update existing subjects' already-saved
marks. Checked the database first: 3 official exams exist (First Unit Test,
Half Yearly Exam, Annual Exam), 327 `official_exam_subject_config` rows
total, 326 at exactly 100 and one already-customized (JR.KG Mathematics on
First Unit Test, max 2, with one mark already entered at 0.00 - safe, not
at 100, left untouched). Ran a single `UPDATE ... WHERE max_marks = 100`
against Supabase directly, changing all 326 rows to 50. Verified
afterward: no official exam has marks entered against any row that was at
100, so no student's already-entered marks became inconsistent with its new
max.

## Current state
- Code change staged, not committed until this entry.
- Database: all 3 official exams' subject configs now at 50 (except the one
  pre-existing JR.KG Mathematics override, untouched).

- Database: `official_exam_subject_config.max_marks` (326 rows, 100 → 50)
