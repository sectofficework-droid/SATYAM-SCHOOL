This one's serious, so I'm putting it in its own section.

I didn't just read the code — I actually tested it. Using nothing but the
public key your app already ships to every browser (the same one anyone
visiting your site technically has access to), I asked the database
directly, with **no login at all**, "give me some rows from `students`" and
"give me some rows from `employees`." I also tried `admin_users` while I
was at it.

**All three handed back real data, no questions asked.** Full student
records (including their app login passwords, in plain text), full
employee records (same), and your admin accounts' names and roles. Anyone
with a browser's dev tools open on your site could technically do exactly
what I just did.

There's actually a rule already written in your database's setup files
that should have prevented this — it says "a student can only see their
own record" — but your mobile app doesn't log in the way that rule expects

on), so as written, that rule should have blocked *everyone*, students
included. Instead it's blocking *no one*. Either that protection got turned
off at some point, or there's an older, more permissive rule from before
this database's setup files existed, still active underneath. I can't tell
which from reading files — that needs one query run directly in your
Supabase dashboard (I already found the exact query someone wrote for this
exact purpose, sitting unused in `mobile-app/SUPABASE_SECURITY_AUDIT.sql`).

**I haven't touched anything.** This is the same kind of fix that got
reverted back in August because it was coded without a plan first — so I
wrote this finding down and I'm waiting for you, same as that one.
