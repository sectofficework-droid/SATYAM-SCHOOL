## 8. You reported login and password reset broken — found it, it was me

You came back saying reset password and login weren't working. This was
the fallout from section 7's own migration, not something new.

I reproduced it directly against production (no guessing): called
`teacher_login`/`student_login` with the same public key the apps use, and
got a real Postgres error back both times, not just "wrong password." Two
separate bugs, both introduced by yesterday's hashing migration:

1. **Wrong column names.** The migration's `CREATE OR REPLACE FUNCTION`
   rewrote `teacher_login`/`student_login` from an old, already-fixed-once
   reference file instead of the actual live, working version — so it went
   back to comparing against `employee_id` (real column: `emp_code`) and
   `enrollment_no` read directly off `students` (it's actually on
   `student_enrollments`, joined). This is a regression of a bug this
   project fixed months ago (`SUPABASE_FIX_COLUMNS.sql`,
   `SUPABASE_TEACHER_CLASS_FIX.sql`, `SUPABASE_SUPPORTING_TEACHERS.sql`,
   `SUPABASE_HELPDESK.sql`) — yesterday's migration silently undid all of
   that. Every teacher and student login was broken since it ran.
2. **`crypt()` unreachable.** Every password function from yesterday pins
   `SET search_path = public`, but Supabase installs pgcrypto into the
   `extensions` schema — so `crypt()`/`gen_salt()` couldn't resolve at all
   inside any of them (login, reset, change-password, verify-password
   alike).

Fixed both, ran them the same way as yesterday (Supabase SQL Editor, your
already-logged-in session), verified live with the same read-only RPC
probe until both returned clean results instead of errors.

While in there, you asked me to also fix a related issue I'd flagged:
**new** students/employees were still getting a plaintext default password
(`app_password` column default was never updated when yesterday's
migration hashed the existing 75 rows) — every account added since would
have hit this same wall. Changed the column default itself to hash at
insert time (`crypt('Satyam@123', gen_salt('bf'))`), so the same default
password now lands correctly stored for every new row automatically.
Confirmed in the Table Editor on both `students` and `employees`.
