## Update — you pointed out I broke something on purpose that shouldn't have
## been broken

You told me the password-view screen was there intentionally, so the admin
could help a teacher or student who's locked out. Fair point, and I should
have handled that better the first time.

Here's the actual constraint: once a password is properly hashed
(encrypted one-way), it is genuinely impossible for anyone — including the
admin, including me, including someone with full database access — to read
the original password back. That's not a setting I can flip; it's what
hashing means. So "view the old password" and "keep it secure" can't both
be true at the same time.

What I built instead: a **"Reset password"** button in the same spot. The
admin clicks it, types (or auto-generates) a brand-new password, saves it,
and sees that new password on screen once — enough to read it out to the
teacher or student standing there — after which it's hashed and stored, not
kept in the clear. Net effect for your front-desk workflow: same outcome
(they walk away with a working password), just no permanent readable copy
sitting in the database waiting to leak.

I also locked this reset action down so only a logged-in admin can use it —
the mobile apps' public key cannot call it.

Note: this reset button only exists for teachers/employees right now, same
as before (there was never a student version of this screen either). If you
want the same "reset" ability for students, tell me and I'll add it — the
database side is already built for it.

**Still pending:** you (or whoever manages the Supabase project) still need
to run `SUPABASE_PASSWORD_SECURITY.sql` in the Supabase SQL Editor — nothing
takes effect until that's done. It now has 5 checks at the bottom instead of
4 (added one for testing the new reset button).
