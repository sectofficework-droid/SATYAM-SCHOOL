Said "code it" with nothing specific pending, so before writing anything
asked which task that meant — confirmed it was the missing error-logging
system flagged earlier today. Checked the mobile app's dependency list
first and confirmed nothing new needed to be added. Wrote out a short plan
(what each app gets, what's deliberately left out for later) and asked for

**What was built, in plain terms:**

- **Admin panel** now has a real error-logging system. When something goes
  wrong — a page crashes, an API call fails, an unexpected JavaScript
  error happens anywhere — it gets written down with a timestamp, what the
  user was doing, and a short ID like `ERR-a1b2c3`. Passwords and similar
  sensitive fields are automatically blanked out before anything is
  logged. If a page crashes outright, instead of a blank/broken screen the
  user now sees "Something went wrong — Diagnostic ID: ERR-a1b2c3" with a
  Try Again button. Managers/senior admins get a small button to download
  the recent log as a file.
- **Mobile apps** (all three — Teacher, Student, Attendance kiosk) get the
  same idea: a background system that catches crashes and errors
  automatically and saves them to a file on the device, even ones that
  would otherwise just close the app silently. Each app has a way to view
  that log: Teacher app under Profile → Settings, Student app on the
  Profile screen, and the Attendance kiosk via a long-press on its
  existing admin settings icon (already PIN-protected).
- No new libraries/packages were needed for any of this.

**Checked, not assumed:** ran the linter on the admin panel (clean) and
the Flutter analyzer on the mobile app — found and fixed two real
mistakes in the first draft before they went anywhere near a device,

**Not yet done:** this hasn't been watched catch a real error on an actual

## Update — same day: cost/privacy check, then an on/off switch

Asked whether lots of users' logs could get expensive or hit Supabase's
free-tier limits. Checked the real database instead of guessing:
currently 19 MB total, after months of real use. The new logging table
would need to fill up with a very large number of tiny error entries
before storage became a real concern — so that specifically isn't the
risk. The actual risk was that nothing stopped one broken feature from
sending the same error over and over automatically. Fixed that: each app
now waits at least 5 minutes before sending the same error again, and
stops entirely after 20 in one sitting, no matter what.

Then: "logging is specifically kept for development purpose not to
collect what users do." That's a fair and important point, so added a
proper on/off switch — a "Logging: ON/OFF" button on the Diagnostics
page. **It defaults to OFF.** Automatic error-catching only runs when
someone with the right access turns it on (meant for when you're actively
chasing a bug), not all the time. The "Report a Problem" button in the
apps still always works regardless — that's a person choosing to send
something, not the app watching them.

One old-fashioned way to avoid piling up data forever: rather than adding
a third scheduled task (checked — the project's two existing ones are
already at what's likely the free-plan limit), old reports over 90 days
old now get cleaned up automatically whenever the Diagnostics page is
opened.

Caught two real mistakes while building this, both before they shipped:
one place where server-side errors would have silently stopped reporting
forever, and one place where the on/off switch would never have actually
loaded due to a startup-order issue. Both fixed; linter and Flutter
analyzer clean afterward, test build of the Teacher app still compiles.

Still outstanding: the database still needs the SQL script run in

Nothing committed.
