## Part B — Auth bypass: found, root-caused, fixed, shipped

### How the report evolved (worth keeping — several early hypotheses were wrong)
1. First framed as "editing URL doesn't authenticate" — investigated
   `AuthGuard.jsx`'s client-only `getSession()` check, found no middleware,
   found `NEXT_PUBLIC_SUPABASE_*` env vars match between `.env.local` (pulled
   via `vercel env pull --environment=preview`) and Production (diffed with a
   throwaway `vercel env pull --environment=production .env.production.check`,
   deleted immediately after — gitignored, never committed).
2. Reframed as bfcache (Back button after logout showing a stale authenticated
   page from browser cache) — real, secondary issue, fixed regardless (see
   below), but not what the user was actually hitting.
3. Reframed as slow redirect ("entering and exiting after a while") — root
   cause there: `router.replace("/login")` requires a client-side RSC fetch
   round-trip; fixed by switching to `window.location.replace("/login")`
   (full navigation, no server round-trip, also fully tears down JS state).
4. Final, correct diagnosis, only reached by **live reproduction** (see
   below): the user was clicking a *different* Logout control than the one
   under test.

### Root cause (confirmed)
`admin-panel/src/components/layout/Sidebar.jsx` had its own, separate Logout
button (bottom-left, user-profile row) that did only:
```js
onClick={() => window.location.href = "/login"}
```
— no `supabase.auth.signOut()`, no `clearAuthUser()`. The Supabase session
token in `localStorage` (`sb-hxkowdaugkkumvzyfsai-auth-token`) and the
persisted Zustand `authUser` (`satyam-school-store`) were **never cleared**.
`Header.jsx`'s separate logout icon (top-right) was already correct. Every
earlier automated test in this session used the header's icon, confirmed it
worked, and therefore couldn't reproduce the user's actual bug — the fix
kept looking "verified" while the real broken control was untouched.

Found via `AskUserQuestion` asking exactly which control the user clicks
("bottom left in ui") — then confirmed with live `claude-in-chrome` browser
automation: logged in real Chrome (extension), read `localStorage` via
`javascript_tool` before/after clicking each control, clicked the sidebar
button specifically, confirmed the token/authUser survived it, then applied
the fix and re-verified the same way — token cleared, `/dashboard` correctly
redirected to `/login` on direct URL entry afterward.

**Rule for next time:** when there's more than one control that plausibly
performs the same action, ask which literal control before trusting a
different one's test result as coverage. Recorded as a note for future
sessions — no rule-book edit made this session (not asked).

### Fixes applied (`admin-panel/`)
1. **`components/layout/Sidebar.jsx`** — Logout button now calls
   `supabase.auth.signOut()` (best-effort) → `clearAuthUser()` →
   `window.location.replace("/login")`, matching `Header.jsx`. Also fixed an
   unrelated adjacent bug found while editing this block: `useStore()` was
   destructuring `user` (doesn't exist in `lib/store.js`, always `undefined`),
   not `authUser` — the sidebar footer always showed the "AU / Admin User /
   Super Admin" placeholder instead of the real logged-in user. Now
   `authUser: user` alias.
2. **`components/AuthGuard.jsx`**:
   - All four `router.replace("/login")` sign-out paths (no-session on mount,
     profile-not-found, `SIGNED_OUT` event, 15-min idle timeout) switched to a
     shared `goToLogin()` helper using `window.location.replace("/login")` —
     instant, no RSC round-trip, fully resets JS state. `useRouter`
     import/usage removed (no longer needed here).
   - Added a `pageshow` listener (`event.persisted`) that re-validates the
     session and redirects if it's gone — closes the bfcache hole (Back
     button after logout showing a stale authenticated page). A `revalidating`
     state hides content synchronously the instant a restore is detected
     (not just after the async check resolves) — first pass showed the
     "Loading..." spinner during this window, but showing that right before
     booting someone out reads as if it's logging them in, so it now renders
     `null` instead for that specific path only (the genuine first-load
     `checking` spinner is unchanged).
   - All `supabase.auth.signOut()` calls wrapped in `try {} catch {}` — a
     failed network revoke call must not block clearing local state/redirect
     (was a real risk: `await supabase.auth.signOut()` throwing would skip
     every line after it).
3. **`components/layout/Header.jsx`** — same `try/catch` around `signOut()`,
   same `window.location.replace("/login")` swap (kept its own `useRouter`
   import — still used by `switchOrg`).
4. **`app/auth/set-password/page.js`** — same `try/catch` around the
   profile-not-found `signOut()` call.

### Verification (live, via `claude-in-chrome`)
Ran the full sequence twice end-to-end in real Chrome against the local dev
server (restarted once mid-session — Fast Refresh didn't fully re-apply a
`useEffect` logic change, confirmed by seeing the bug persist on a stale

login → `localStorage` confirmed populated → click **sidebar** Logout →

`/dashboard` → correctly redirected to `/login`, zero unauthenticated access,
no content flash. Also independently re-verified the header icon still works
and the bfcache/bfcache-null-render path.
