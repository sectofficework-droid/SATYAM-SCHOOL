## What this confirms from -1/-2

Ran ~225 seconds (21 poll ticks) on a live camera feed, including one full
successful match. From the on-screen debug HUD and `adb logcat -s flutter`:

- **Decode count: 1 per attempt, every attempt, no exceptions.** Was 5
  before this session's fix. Confirms `decodeOriented` + the shared-decode
  refactor across `detectSingleFace`/`isExposureUnusable`/`isTooBlurry`/
  `livenessScore`/`getEmbedding` works exactly as designed.
- **No overlapping polls.** Ticks ran strictly 1, 2, 3 ... 21 in sequence,
  each starting ~1s after the previous one's `_autoCapture()` fully
  returned. Confirms `_scheduleNextPoll`'s one-shot self-rescheduling
  design works.
- **Main-isolate stalls: 3 total across 225s, all brief (287ms, 457ms,
  446ms), none repeating.** All three line up with one-time costs (first
  TFLite inference / JIT, not per-poll decode work). This is the direct
  disproof-or-confirmation the stall watch was built for in -1, and it
  confirms the original theory (five decodes per poll blocking the main
  isolate every second) is fixed — there is no longer a recurring stall
  pattern.
- **Camera never reinitialized.** Stayed on `gen1` for the entire run,
  including through a full match → native confirm dialog → declined
  ("Not Me") → Enter Code screen → closed back → resumed cleanly (this
  exercises the exact navigation path the 2026-09-09 session's Bug 1 fix
  covers — confirmed still working: `LIFECYCLE ... resumed` followed by
  polling picking back up with no manual intervention needed).
- **One graceful `takePicture` failure, expected and handled correctly**:
  closing the page mid-poll (tapping the X) hit
  `A CameraController was used after being disposed` — this is the exact
  benign race `_autoCapture`'s own comment describes, and it was
  handled exactly as designed (logged, silently swallowed, no crash, no
  scary error shown to whoever's at the kiosk).
- **A full recognition cycle genuinely works.** One attempt detected a
  real face, passed the exposure/blur gates (4ms / 75ms — near-instant now,
  versus doing their own decode before), scored 0.992 on liveness
  (threshold 0.45), matched an enrolled staff member (`best=0.624` against
  `kMatchThreshold=0.6`, margin `0.159` against `_matchMargin=0.05`), and
  correctly rendered the native confirm dialog with the matched name. Test
  declined via "Not Me" rather than confirmed, specifically to avoid
  writing a test attendance record to production (no branch/staging
  environment exists for this project, confirmed in the 2026-09-09
  session) — **no data was written**.

## What this session found that -1/-2 did NOT anticipate

**`CameraController.takePicture()` itself is slow on this camera — 3.6 to
5.8 seconds per call, averaging ~5.5s across 20 calls** (min 3613ms, max
5774ms). This is the dominant cost of every poll cycle by a wide margin —
roughly 100x the ~50ms the shared decode now takes, and unrelated to
anything this session's fix touched. It is a native camera-plugin call, not
Dart-side image processing, so it does not show up as a `ScanTrace` main-
isolate stall (and none of the 3 stalls recorded coincide with a
`takePicture` call) — but a human standing at the kiosk waiting 4-6 seconds
for anything to happen every cycle would very plausibly describe that as
"freezing," independent of whatever the Dart code does with the photo
afterward.

**Not yet known: whether this is BlueStacks-specific or also true on the
real kiosk hardware.** The existing code comments in `face_punch_page.dart`
already document BlueStacks' virtualized camera being unstable ("Unable to
set 25 fps" / "Surface had no valid native window" from a prior session's
logcat), so a slow/flaky `takePicture()` on this same virtualized camera is
consistent with a known-flaky environment rather than necessarily a
property of the app or of real camera hardware. This needs testing on the
actual physical kiosk tablet to know whether it's relevant at all outside
BlueStacks.

   about it** — it's a materially different problem from what was

   camera-capture latency). Recommend testing on the real kiosk tablet

2. If it does reproduce on real hardware, likely next things to try (not
   yet investigated, no code written for any of these): lowering
   `ResolutionPreset` below `.medium`, checking whether autofocus/auto-
   exposure lock is what `takePicture()` is waiting on, or whether the
   camera plugin has a faster capture path than a full still photo for
   this use case. None of this is scoped or approved yet.
3. Items 2 (off-main-isolate) and 4 (reconsider still-photo-per-poll) from
   -1's original proposal remain open but are now lower priority — the
   stall watch shows the main isolate is not the bottleneck any more;
   `takePicture()` latency is.
