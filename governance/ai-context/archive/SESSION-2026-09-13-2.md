## Work done file-by-file

1. **`mobile-app/lib/core/services/face_recognition_service.dart`** —
   added `decodeOriented(String imagePath)`: reads, decodes, and
   `bakeOrientation`s the JPEG exactly once, using the existing traced
   `_decode` funnel. The five recognition entry points now take that
   decoded `img.Image?` instead of a file path and re-decoding it
   themselves:
   - `detectSingleFace(imagePath, decoded)` — `decoded` is only used to
     decide whether ML Kit gets an exposure-corrected copy
     (`_exposureCorrectedCopy` no longer decodes on its own); a null
     `decoded` (shared decode failed) just skips that correction and lets
     ML Kit try the original file, matching the prior per-function
     fail-open behaviour.
   - `isExposureUnusable(decoded)`, `isTooBlurry(decoded, face)`,
     `livenessScore(decoded, face)`, `getEmbedding(decoded, face)` — no
     path parameter at all now; each keeps its original hard-reject-on-null
     semantics (`true`/`null`) if the shared decode failed, same as when
     each used to fail its own independent decode.
   Net effect: **one JPEG decode per scan attempt instead of five.**
   Behaviour of every quality gate, liveness check, and match is otherwise
   unchanged — same thresholds, same crop math, same orientation handling
   (still `bakeOrientation` once, just shared now instead of repeated).

2. **`mobile-app/lib/app/modules/attendance_kiosk/face_punch_page.dart`** —
   two changes:
   - Calls `decodeOriented` once per attempt in `_autoCapture` and passes
     the result to all five recognition calls (updated call sites).
   - Replaced the `Timer.periodic(_pollInterval, ...)` poll with a
     self-rescheduling one-shot `Timer` (`_scheduleNextPoll`): the next
     poll is armed only after the previous `_autoCapture()` has fully
     finished (`try`/`finally`), and only while still mounted and on
     `_Stage.camera`. Previously the periodic timer fired into a running
     attempt every ~1s regardless of whether that attempt had finished;
     overlapping fires were harmless (a re-entrancy guard, `_busy`, just
     skipped them) but were also the mechanism asking the camera for a
     fresh photo once a second even while still processing the last one.
     The `_busy` guard and its `POLL … SKIP` log line stay in place as a
     defensive fallback (comment updated to say so) but should no longer
     fire in normal operation.
   - Updated the two explanatory comments (class header, `_initCamera`)
     that described the old periodic-timer behaviour.

3. **`mobile-app/lib/app/modules/attendance_kiosk/face_enroll_capture_page.dart`**
   — same recognition-service signatures apply here too (enrollment shares
   the service). Updated its `_autoCapture` to call `decodeOriented` once
   and pass it to `detectSingleFace`/`isExposureUnusable`/`isTooBlurry`/
   `getEmbedding` the same way. This file wasn't in scope of the original
   bug report, but its calls would not have compiled against the new
   signatures otherwise, and it has the same "several checks re-decoding
   the same photo" shape (just without a 1s poll driving it, since
   enrollment is a slower, prompted multi-shot flow) so the same-decode fix
   is a correctness improvement there too, not just a compile fix.

All instrumentation added in -1 (`ScanTrace`, `ScanDebugHud`, the per-stage/
per-tick/per-camera-generation logging) is untouched and still active in
debug builds — it will now additionally show `decodesThisAttempt` settling
at 1 instead of 5, which is the way to confirm this fix actually landed once
someone can run it.

## What's still open (from -1's proposed fix, items 2 and 4)

2. **Move the `image`-package work off the main isolate.** Not done. This
   is what would fully eliminate any UI-thread stall regardless of how many
   decodes remain; item 1 above only cut the per-attempt cost roughly 5x, it
   didn't move the work off the thread that paints the screen. If a stall
   still shows up in the `ScanTrace` stall watch after this fix is tested,
   this is the next thing to do.
4. **Reconsider still-photo-per-poll.** Still an open design question, not
   attempted.
