# SESSION-2026-09-13-1 — Kiosk face-scan: instrumented the capture pipeline (diagnosis, fix NOT applied)

restarting again and again; make it debug"*. Scope taken: the attendance

## Diagnosis (from reading the code — NOT yet confirmed on-device)

`_autoCapture()` fires on a 1000ms `Timer.periodic` and runs the entire
recognition pipeline **on the main isolate**. One poll performs **five
independent full-JPEG decodes of the same photo**, each a `readAsBytes` +
`img.decodeImage` in pure Dart, plus several whole-image pixel walks and
three TFLite invocations:

| Stage (in call order) | Decodes the JPEG | Also does |
| --- | --- | --- |
| `detectSingleFace` → `_exposureCorrectedCopy` | 1 | `bakeOrientation`, `_averageLuminance`, sometimes `adjustColor` + `encodeJpg` + a disk write |
| `isExposureUnusable` | 1 | `_averageLuminance` |
| `isTooBlurry` | 1 | `bakeOrientation`, crop, grayscale, `_laplacianVariance` |
| `livenessScore` | 1 | `bakeOrientation`, 2 crops + 2 MiniFASNet runs |
| `getEmbedding` | 1 | `bakeOrientation`, crop, resize, histogram-equalize, MobileFaceNet run |

`img.decodeImage` is a synchronous pure-Dart JPEG decoder. There is no
`compute()` and no isolate anywhere in `face_recognition_service.dart`. A
`ResolutionPreset.medium` still frame is 720x480 to 1280x720 depending on
the sensor, so each decode is plausibly in the hundreds of milliseconds, and
the pixel-walk loops (`getPixel` per sample) sit on top of that.

That accounts for both halves of the report:

- **"freezing"** — while `_autoCapture` runs, the Dart UI isolate cannot
  build a frame, so `CameraPreview` stops updating. The preview looks dead
  even though the native session is healthy. No exception is logged, which
  is exactly why this has been hard to pin down.
- **"restarting again and again"** — the poll timer keeps firing during the
  stall. Those fires hit the `_busy` guard and return, so they are currently
  invisible (the guard has no logging). Each *successful* poll additionally
  calls `takePicture()`, which re-arms a still capture on the session once
  per second, indefinitely, for as long as someone stands at the kiosk.
  Sustained allocation churn (five full bitmaps per second) is also a
  credible route to the HAL/session restarts that `_reinitCamera`'s own
  comment already documents seeing on BlueStacks.

Worth stating plainly: this is **not** the 2026-09-09 freeze
(`SESSION-2026-09-09-1.md` Bug 1, the un-resumed `pausePreview` on route
pop). That one was a specific navigation path and is fixed. This one needs
no navigation at all — it happens while simply standing at the scan screen.

## Work done file-by-file

1. **`mobile-app/lib/core/utils/scan_trace.dart`** (NEW, 108 lines) —
   `ScanTrace` singleton. `log(tag, msg)` writes a `[SCAN]`-prefixed line to
   logcat *and* into a 60-line ring buffer. `step(label, body)` times an
   async stage and logs its duration, re-logging then rethrowing on failure
   so a stage that dies at 4s is distinguishable from one that dies
   instantly. `startStallWatch()` runs a 100ms timer and logs any fire that
   is 250ms or more late. **That stall watch is the key measurement** — a
   Dart timer can only run late if the isolate was blocked, so its lateness
   *is* the freeze, measured directly rather than inferred. Everything is
   gated on `kDebugMode` and compiles out of release builds.

2. **`mobile-app/lib/core/services/face_recognition_service.dart`** —
   instrumented, behaviour unchanged. The five public entry points
   (`detectSingleFace`, `isExposureUnusable`, `isTooBlurry`,
   `livenessScore`, `getEmbedding`) are now thin `ScanTrace.step` wrappers
   around untouched `_`-prefixed bodies. The five inline
   `readAsBytes`/`decodeImage` pairs now go through one `_decode(path,
   caller)` funnel that logs KB, read ms, decode ms, resulting dimensions,
   and a per-attempt decode counter (`decodesThisAttempt` /
   `resetDecodeCounter()`) — so the log literally reads `#1 exposureCorrect`
   through `#5 embedding` per scan attempt, making the repetition
   self-evident. ML Kit's `processImage` and all three `interpreter.run`
   calls are timed individually.

3. **`mobile-app/lib/app/modules/attendance_kiosk/face_punch_page.dart`** —
   instrumented, behaviour unchanged. Added: a `WidgetsBindingObserver` that
   logs every `didChangeAppLifecycleState` with the controller's generation
   and `isInitialized` (a controller surviving a background/foreground cycle
   onto a dead session is the *other* classic frozen-preview cause, and this
   tells the two apart); a `_cameraGeneration` counter so every line says
   which controller instance it came from; camera init/reinit/failure
   logging; per-tick `POLL` lines including **every skipped fire with its
   reason** (`busy=true` vs `initialized=false` — different root causes);
   timing of `takePicture`; and outcome lines carrying face box size,
   eye-open probabilities, liveness score vs threshold, and match
   best/second similarity vs threshold.

4. **`mobile-app/lib/app/modules/attendance_kiosk/scan_debug_hud.dart`**
   (NEW, 60 lines) — an `IgnorePointer` overlay pinned to the bottom of the
   scan screen showing the last 12 trace lines, red for `STALL`/`THREW`.
   Renders `SizedBox.shrink()` outside `kDebugMode`. It exists because the
   kiosk tablet normally sits in the office with no laptop attached, so
   "reproduce it, then read the last few seconds" has to work without adb.

## Proposed fix — NOT APPLIED, needs "code it"

In the order the evidence should be read:

1. **Decode once per attempt, not five times.** Decode plus
   `bakeOrientation` once in `_autoCapture` and pass the `img.Image` down.
   Removes four of the five decodes outright. Biggest win for the smallest
   change, and it alters no threshold and no decision.
2. **Move the pipeline off the main isolate** (`compute`/`Isolate.run` for
   the `image`-package work). This is what actually stops the UI freezing;
   item 1 only shortens it. TFLite interpreters and ML Kit detectors are not
   isolate-portable as they stand, so this needs care, not a blanket wrap.
3. **Stop the poll timer while an attempt is in flight** and restart it
   after, instead of letting it fire into the `_busy` guard once a second.
   `Timer.periodic` plus a re-entrancy flag is the wrong shape for work that
   can outlast its own interval.
4. **Reconsider the still-photo-per-poll design.** The service's header
   comment argues for JPEG stills over a frame stream (EXIF orientation
   handled for you, versus manual YUV420-to-RGB plus rotation math). That
   reasoning is sound and should not be overturned casually. But it was
   written for *one photo per button press*; the screen now takes one every
   second, which is a different cost profile than the comment was weighing.

Items 1 and 3 are contained and low-risk. Item 2 is a real refactor of a
production path. Item 4 is a design question, not a patch. Recommend
approving 1 and 3 first, re-measuring with the trace, then deciding on 2.
