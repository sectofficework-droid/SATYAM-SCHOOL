## Objective

basic fields (Class, Student Name, Father Name, Mother Name, DOB, Mobile 1,
Mobile 2, Address) that auto-assigns enrollment numbers and leaves students
immediately usable in the mobile app (login, homework, marks). Separately,
add a Super Admin import that replaces a student's data by matching
Enrollment No, for backfilling full details later. Student list needed to

## Work done this session
Plan-mode design (see chat transcript / plan file, not duplicated here),
then implemented in full:

1. **`mobile-app/SUPABASE_STUDENT_BASIC_IMPORT.sql`** (new) — adds
   `students.data_status TEXT NOT NULL DEFAULT 'Complete'`. **Not yet run
   against production Supabase** — user needs to run this before the
   feature works end-to-end (flagged to the user directly in-session).
2. **`admin-panel/src/lib/studentService.js`** — `addStudent()` now writes
   `data_status: formData.dataStatus || "Complete"`; `updateStudent()`
   unconditionally writes `data_status: "Complete"` (any full-form save
   clears the Incomplete flag, not just the dedicated replace-import tool);
   `mapToStudent()` exposes `dataStatus`; `getStudents()` and
   `getStudentByEnrollment()` select `data_status`.
3. **`admin-panel/src/lib/importUtils.js`** (new) — `normalizeDate()` and
   `normalizeAgainstList()` extracted out of `super-admin/page.js` (were
   private local functions there) so the new Basic Details import can reuse
   them without duplicating the date/fuzzy-match logic. `super-admin/page.js`
   now imports both from here instead of defining them locally.
4. **`admin-panel/src/components/BasicDetailsImportModal.js`** (new) —
   Student-module modal: `.xlsx` template (3 header rows, DOB column
   Text-formatted like the existing Super Admin importer), parses/validates
   against a live `getClasses()` call (not a hardcoded list), splits
   "Student Name" into first/last on the first space, calls `addStudent()`
   per row sequentially with `dataStatus: "Incomplete"`, post-insert
   mismatch check, incremental import log.
5. **`admin-panel/src/app/(dashboard)/super-admin/page.js`** — new
   `FullDetailsReplaceImportPanel` component: same `IMPORT_FIELDS` template
   as the existing `ImportStudentsPanel`, plus a required leading
   "Enrollment No" column; on confirm, looks the row up via
   `getStudentByEnrollment()` and calls `updateStudent()` (never inserts);
   unmatched enrollment numbers are logged as row errors, never silently
   skipped. Wired into both the Senior Admin tab bar and the Management
   Head "students" sub-tab bar as "Replace Full Details" (`RefreshCw` icon,
   already imported).
6. **`admin-panel/src/app/(dashboard)/student/page.js`** — "Import Basic
   Details" button next to "Add New Student"; a new "Details" filter chip
   (Incomplete, with live count, mirrors the existing `DOC_FILTER_OPTIONS`
   chip pattern); an amber "Incomplete" badge on both the desktop header
   strip and the mobile card, additive to the existing Active/Left/Promoted
   badge.

## Decisions made (no separate approval round — implementation-detail level,
not requirement/architecture changes; see plan file for full reasoning)
- Basic-import students default to section "A" (matches the existing single
  Add Student form's own convention) rather than leaving `section_id` NULL.
- App login for basic-imported students relies on the same DB-level
  `app_password` bcrypt default that the ordinary Add Student form already
  depends on today (`addStudent()` never sets it explicitly either way) —
  no new code needed, no new assumption beyond what's already load-bearing
  in production.
- `updateStudent()` clears `Incomplete` unconditionally on every call, so a
  normal Edit Student save also completes the record, not only the
  dedicated replace-import tool.
