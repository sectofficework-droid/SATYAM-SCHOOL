# SESSION 2026-08-28-1 — Admin "Access Code" impersonation module

## What was asked
User: "I want to build such a module where developer/admin (master/super)
can access any account of student/teachers in order to keep full control /
test without needing their private/custom password."

## Research (before planning)
Two Explore-agent passes established the real auth architecture (not
assumed — read the live RPC definitions):
- Mobile-app login is **not Supabase Auth**. `teacher_login`/`student_login`
  (`mobile-app/SUPABASE_FIX_LOGIN_REGRESSION.sql`) are `SECURITY DEFINER`
  Postgres functions granted to `anon`, bcrypt-checking `app_password`, that
  return a JSON profile blob. `AuthService._saveSession` in
  `mobile-app/lib/core/services/auth_service.dart` just caches that JSON in
  `flutter_secure_storage` — no JWT, no `auth.uid()`-scoped RLS to piggyback
  on for student/teacher data.
- Admin-panel auth **is** real Supabase Auth (`supabase.auth.signInWithPassword`),
  backed by an `admin_users` table (`id = auth.users.id`, roles `management`
  / `senior_admin` / `normal_admin`), gating pattern already established by
  `admin_reset_student_password`/`admin_reset_employee_password`
  (`mobile-app/SUPABASE_HASH_APP_PASSWORD.sql`).
- No prior impersonation/"login as" feature existed anywhere in the repo.

This meant the natural design wasn't "forge a session" (there is none) but a
deliberate, audited **one-time access code**: admin panel generates it,
mobile app redeems it through the same JSON-blob shape the real login RPCs
already produce, so it drops straight into the existing session-save path.

## What was built
New file `mobile-app/SUPABASE_IMPERSONATION.sql`:
- Tables `impersonation_codes` (short-lived, opportunistically pruned) and
  `impersonation_audit_log` (permanent, one row per `created`/`redeemed`/
  `redeem_failed` event, denormalized `target_label`/`created_by_name` so
  history survives the token row or the source rows changing later).
- `create_impersonation_code(p_target_type, p_target_id)` — `SECURITY
  DEFINER`, checks `admin_users.role IN ('management','senior_admin')`
  against `auth.uid()` **inside the function itself**, not just the UI.
  8-char code from a 32-symbol alphabet (`ABCDEFGHJKLMNPQRSTUVWXYZ23456789`,
  no `0/O/1/I/L`) — chosen over a 6-digit numeric OTP because entropy is the
  real defense here (see security fix below), not IP rate limiting, which
  Supabase's connection pooler makes unreliable to implement correctly
  anyway (`inet_client_addr()` inside `plpgsql` sees the pooler's IP, not
  the real client's).
- `redeem_impersonation_code(p_code, p_expected_role)` — granted to `anon`
  (matches the trust model of `teacher_login`/`student_login`).
  `p_expected_role` comes from the app's own `AppConfig.lockedRole`, never
  user-typed, so a code can't be redeemed in the wrong app build. Single-use
  claim is atomic (`UPDATE ... WHERE used_at IS NULL ... RETURNING`, closing
  the TOCTOU race a `SELECT` then `UPDATE` would have). A role mismatch
  still burns the code (claimed `used_at` before the mismatch check) so a
  wrong-app guess isn't retryable. Every failure path writes an audit row
  with a `detail` reason (`not_found`/`already_used`/`expired`/
  `role_mismatch`/`target_deleted`).
- `get_impersonation_audit_log(p_limit)` — for the admin panel's log tab,
  same `management`/`senior_admin` gate.
- Two internal helpers `_impersonation_employee_json`/`_impersonation_student_json`
  build the identical JSON shape `teacher_login`/`student_login` already
  return, by id instead of credentials — kept separate from the real login
  functions deliberately (this file's own history shows how fragile those
  two are to edit blind).

## Security bug found and fixed same session
After the first migration was live, direct-RPC verification (via a
throwaway Node script using the service-role key — deleted after) found
`create_impersonation_code` rejected an unauthenticated `anon` caller with
`Not authorized` — expected, that's the internal check working. But probing
further: `_impersonation_employee_json(<any real employee id>)`, called
**directly** by `anon`, returned that employee's full profile with **zero**
authorization check. Root cause: PostgreSQL grants `EXECUTE` on every new
function to `PUBLIC` by default, and the migration only ever added `GRANT`s
— never `REVOKE`d the implicit `PUBLIC` grant. The two internal helpers have
no auth check of their own (they trust only `redeem_impersonation_code` to
call them) — so any client holding nothing but the public anon key (i.e.
anyone) could pull any student's or teacher's full profile with no code, no
login, nothing. **Live-confirmed exploitable** before fixing (pulled a real
teacher's data via the anon key as proof), same live-verification discipline
as the 2026-08-21 RLS finding.

Fixed same session: `mobile-app/SUPABASE_FIX_IMPERSONATION_GRANTS.sql` —
`REVOKE EXECUTE ... FROM PUBLIC` on all five functions, then re-asserts only
the intended `GRANT`s. Applied to production the same way (Supabase
dashboard, user pasted). Re-verified after: the same anon-key probe now
returns `permission denied for function _impersonation_employee_json`; the
full generate→redeem→reuse→audit-log flow re-tested and still works
correctly for the legitimate path.
