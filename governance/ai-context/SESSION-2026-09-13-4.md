# SESSION-2026-09-13-4 — takePicture() latency: flash-mode theory tried, disproven; pivoting to real hardware

## Objective

Direct continuation of `-3`'s open finding (`takePicture()` taking 3.6-5.8s
per call on BlueStacks). User asked "how to fix that camera plugin issue",
then mid-investigation reported the original symptom "still behaving like
it was behaving before" — consistent with `-2`'s fix (decode-once +
gated-poll) never having touched `takePicture()` itself, exactly as `-3`
flagged as unconfirmed.

## Investigation

Confirmed via `.flutter-plugins-dependencies` and `pubspec.lock` this
project resolves to `camera_android_camerax` 0.7.4+4 (CameraX-based), not
the legacy `camera_android` (Camera2-based) implementation. Read the
plugin's `ImageCaptureProxyApi.java`: the app never calls `setFlashMode`,
so CameraX's `ImageCapture` is built with whatever the Dart-side
`CameraController` defaults to — confirmed in `camera` 0.12.0+2's own
source (`camera_controller.dart` line 64) to be **`FlashMode.auto`**.
CameraX is documented (multiple upstream issue reports) to run a full
auto-exposure "should I flash" precapture metering sequence before a still
capture when flash isn't explicitly off, which can stall for seconds on a
camera that never signals 3A convergence — a virtualized/passthrough camera
being a plausible candidate for exactly that. The near-constant clustering
of the measured times (5.5-5.9s across most samples, not randomly
distributed) looked like the signature of hitting an internal wait/timeout,
consistent with this theory.

Also checked whether CameraX's `ImageCapture` capture mode
(`CAPTURE_MODE_MINIMIZE_LATENCY` vs. the quality-prioritizing default,
another documented cause of slow CameraX stills) is exposed by the Flutter
plugin at all — grepped the plugin's Java and Dart sources for
`CaptureMode`/`MINIMIZE_LATENCY`: **no matches**. The plugin's
`ImageCaptureProxyApi.pigeon_defaultConstructor` never calls
`ImageCapture.Builder.setCaptureMode()`, so this isn't tunable from the app
side without forking the plugin.

## Fix tried

Added `await controller.setFlashMode(FlashMode.off)` right after
`controller.initialize()` in both `face_punch_page.dart` and
`face_enroll_capture_page.dart` (mirrors the change in `-2`/`-3`'s files).
Rebuilt, reinstalled on the same BlueStacks emulator, cold-started the app,
and re-measured `takePicture()` directly via the still-active `ScanTrace`
instrumentation.

## Result: DISPROVEN

`setFlashMode(off)` itself applied instantly (`STEP setFlashMode(off) ok in
2ms`). But `takePicture()` timing was **unchanged**: 3996, 5181, 5752,
5672, 5760, 5830, 5786ms across 7 calls — statistically indistinguishable
from `-3`'s pre-fix numbers (3613-5774ms, avg ~5.5s). Flash-mode precapture
metering was not the cause, or at least not the dominant one.

The `FlashMode.off` call was **left in place** — it's a harmless, correct
default override regardless (the front camera used here has no flash
hardware on essentially any Android device, so nothing is lost), but the
comments explaining it were rewritten to say plainly that it did not fix
the latency, rather than leave a misleading "this fixes it" claim in
production code. See the updated comments in both files.

## Decision: stop guessing on BlueStacks, test real hardware next

Two rounds of app-level tuning attempts (decode/poll fix in `-2`, flash
mode in this session) have not resolved `takePicture()` latency, and the
plugin doesn't expose the other documented lever (capture mode) without
forking it. Presented the user three options — keep digging on BlueStacks,
try swapping to the legacy Camera2 engine (`camera_android` instead of
`camera_android_camerax`, a bigger change requiring full re-verification of
preview orientation/sizing on both camera screens), or stop and test the
real kiosk tablet first since BlueStacks' virtual camera is already
documented elsewhere in this codebase as unreliable and nothing so far
confirms this latency exists outside it. **User chose: test the real kiosk
tablet first.**
