## Two real bugs found during end-to-end verification (not pre-existing —
## both introduced or exposed by this session's own changes, both fixed
## same session)

**Bug 1 — kiosk camera freeze.** `face_punch_page.dart` calls
`controller.pausePreview()` before showing the native confirm dialog. Backing
out via "Not Me" → Enter Code screen → close (X) returned to a frozen last
frame — GetX's `Get.back()` route pop never resumed the paused camera or
reset `_stage`, so the kiosk just sat there doing nothing (would neither
rescan nor return home). **User caught this live** while watching the
BlueStacks test session run ("when i press not me enter code and return to
face scan; face freezes nothing happens"). Fixed: both navigation call sites
(`_enterCodeInstead` and the inline "Not Me" branch in `_autoCapture`) now
`await` the pushed route, then `resumePreview()` and reset to
`_Stage.camera` once it's popped.

**Bug 2 — wrong role in the prior session's grants.** Verified via
`grep -rln "\.auth\." mobile-app/lib` = **zero matches** — none of the three
Flutter apps (kiosk/teacher/student) ever call Supabase Auth's sign-in; they
all use a custom app-level login (per the existing REQ-SEC-002 note in
`TODO.md` about `employees`). This means **every** request from **any**
Flutter app flavor, including the teacher app's own self-service checkout
button, executes as the `anon` Postgres role — never `authenticated`. Only
the admin panel (Next.js, real `@supabase/ssr` sign-in, confirmed via
`grep -rln "auth.signIn\|createServerClient\|createBrowserClient" src/`) is
actually `authenticated`. The prior session's migration granted
`record_check_out` EXECUTE and `employee_shifts` SELECT to `authenticated`
only — this silently broke the teacher app's checkout and the new
shift-list fetch with `PostgrestException: permission denied for table
employee_shifts, code 42501`, surfaced live via `flutter run` log tail
during BlueStacks testing. Compounding it: `teacher_my_attendance_page.dart`'s
`_load()` had no try/catch around the new fetch, so the unhandled exception
left the page spinning forever (`_loading` never flips false) — the user
independently reported this exact symptom mid-session ("app ui shows 9:23 am
check in and check out says some error why?") before the root cause was
found via the log tail.
**Fixed live**: `GRANT EXECUTE ON FUNCTION record_check_out(...) TO anon;`
and `GRANT SELECT ON employee_shifts TO anon;` applied via
`apply_migration`, and `mobile-app/SUPABASE_MULTI_SHIFT_MIGRATION.sql`
updated to grant both roles with an explanatory comment, so a future session
reading that file doesn't repeat the same mistake on the next RPC/table this
feature (or any future one) adds.
**This is a systemic fact worth carrying forward past this session**:
"authenticated" in this codebase's Postgres grants only ever means the admin
panel — never any of the three Flutter apps. Relevant to `TODO.md`
REQ-SEC-002 (anon over-exposure) — that item's `employees`-table note
already said the mobile app "reads/writes it directly with the anon key for
the teacher's own profile (no real session)"; this session confirms that's
not an `employees`-specific exception, it's true of literally every Flutter
<-> Supabase call in the app. Added a note to REQ-SEC-002 in `TODO.md`
reflecting this (see Files changed below) — not a new item, a
generalization of the existing one, so nothing else in that item was
re-litigated.

employee record (`employees.id = 7f9b54ab-7a21-496c-885e-b3c838814465`, "BK
Debiprasad Das") after being asked, given no QA test accounts currently
exist (per `test_admin_accounts` cross-session memory — deleted
2026-08-27). Verified via a mix of the real kiosk/teacher app UI (face-match
worked live against the BlueStacks host webcam) and direct RPC calls (used
when the UI's own camera/timer behavior made a specific step
impractical to force deterministically, e.g. re-triggering a face match on
demand):

  duplicate row inserted, confirmed via direct query after the attempt.
- `record_check_out` closes whichever shift is open; confirmed via query.
- A second `record_face_punch` after checkout correctly opens shift #2 —
  confirmed via query, and the teacher app's My Attendance banner rendered
  all shifts of the day (screenshotted with 3 shift rows after further
  ad hoc testing, see below).
- Admin-panel grant path (`authenticated`) was never broken — only the
  Flutter/`anon` path was, per Bug 2 above.

**Test-data handling, and a mistake made and corrected within this
session:** cleaned up the test `employee_shifts` rows afterward as agreed,
but the cleanup query (`DELETE FROM employee_attendance WHERE employee_id=...
AND date=...`) removed the **entire** day's row unconditionally — which
included a genuinely real, pre-existing check-in (`check_in_at =
2026-09-09 09:23:40 UTC`, `punch_method='face'`) from earlier that day,
unrelated to this session's testing (predates this session's first write by
~2h45m). This is the same row the user had asked about mid-session ("app ui
shows 9:23 am check in") — at the time it was treated as pre-existing noise
without confirming whether it predated the session; it did, and deleting it
was a real mistake, not a no-op. **Caught and fixed same session**: the
exact original values (captured in an earlier query, before the delete) were
re-inserted via `ON CONFLICT DO UPDATE`, restoring `check_in_at`/
`check_out_at`/`status`/`punch_method` exactly. `id`/`created_at` differ
(new row) — nothing in the app reads either column meaningfully, but noting
it for completeness. No `employee_shifts` row existed for that same
9:23 AM check-in (correctly — that table didn't exist yet at 9:23 AM, the
prior session's migration applied later that morning), so nothing needed
restoring there.
**Lesson for future sessions**: when cleaning up test data on a *real*
person's record, check whether a row predates the session (`created_at`, or
values captured before any test writes began) before bulk-deleting it as
presumed test noise — this cross-references `feedback_verify_implausible_
values_dont_explain_away` in cross-session memory, which already flagged
"odd value → trace it, don't explain it away" as a standing rule; this
session is a concrete instance of not fully following that rule the first
time it mattered.
