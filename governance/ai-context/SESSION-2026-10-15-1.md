## Pre-existing pieces this reused (found during discovery, not built new)
- `admin-panel/src/lib/staffLeaveService.js`'s `saveEmployeeAttendanceForDate(records)`
  — upserts `{employee_id, date, status}` onto `employee_attendance`
  (`onConflict: "employee_id,date"`). Since the payload only carries those
  three keys, Supabase's upsert only updates those columns on conflict —
  `check_in_at`/`check_out_at`/`punch_method` (written exclusively by kiosk
  punches) are left untouched. This is the exact mechanism the Employee
  module's `MarkStaffAttendanceTab` (`employee/page.js`) already depends on
  for its own single-day P/A editing — the grid reuses it unchanged rather
  than inventing a new write path.
- `admin-panel/src/lib/reportService.js`'s `getStaffAttendanceForReport()`
  — already fetches *all* `employee_attendance` rows (every employee, every
  date) into `report/page.js`'s `dbStaffAttendance` state on page load. The
  grid pivots this same in-memory array into employee×day cells instead of
  issuing a new query; it re-calls this function (not `loadAll()`) on a
  debounce after edits to resync just the staff-attendance slice.
- The `showExamsReport` early-return pattern already in `report/page.js`
  (around where `rType`/`staffView` are read) — copied for the new
  `staffView === "grid"` branch so the generic column-selector/summary/
  export/table JSX (which doesn't apply to a pivoted grid) didn't need
  threading-through with conditionals.

## Design decisions not already covered by the AskUserQuestion answers
- **No in-grid delete/clear.** Cycling (P→A→L→P) and direct typing (P/A/L)
  never produce an "unmarked" state — only the existing confirm-dialog
  delete (Daily/Per-Employee views, unchanged) removes a record outright.
  Chosen so a fast run of keystrokes while editing a row can't accidentally
  wipe a day's record.
- **Roster = employees with at least one attendance row in the selected
  month**, not the full employee list. Matches the existing Daily/
  Per-Employee views' behavior (both are also sourced from
  `dbStaffAttendance`, not the separate `dbEmployees` report dataset, which
  is shaped differently - `role`/`subject` fields, not
  `designation`/`department`) - not a new limitation introduced by this
  change.
- **No working-day/holiday gating.** Only future dates (`> todayStr`) are
  disabled. Sundays/holidays stay editable, consistent with how the
  Employee module's existing single-day Mark Attendance tab already has no
  such gate (there is also no established "holiday calendar applies to
  staff too" concept anywhere in the staff-attendance code paths, so
  inventing one here would have been scope creep beyond what was asked).
- Future-date cells are kept **focusable but inert** (not `disabled`) so
  keyboard arrow navigation can move across them without desyncing which
  DOM node actually holds focus (a `disabled` button can't receive
  `.focus()`, which would have frozen arrow-key navigation at the first
  future-date column).
- Table uses `border-separate`/`border-spacing-0` rather than
  `border-collapse` - required for `position: sticky` header row + sticky
  first column to render correctly together across browsers.

# Same session, immediate follow-up — REQ-FEAT-011: manual check-in time

## What triggered it
Right after REQ-FEAT-010 shipped, user: "this only marks absent present no
way to mark time speciall day late time how?" Read as: the Grid only
touches `status` - no way to record an actual arrival time, and a
reference to "special day" that turned out to point at a real, separate
existing feature (`kiosk_special_day_overrides` /

for a specific future date, e.g. an exam day) this session hadn't

`employee_shifts` grants while scoping the fix, not because the user named
the file.

## Clarification (AskUserQuestion, bundled, before coding)
1. Where to enter a time - inside the Grid cell, the Daily view, or both →
   **inside the Grid cell**.
2. What to capture - check-in only, or check-in + check-out → **check-in
   only**.
3. How Late/On-Time is decided for a hand-entered time - auto-compute from
   Settings' expected-start-time + grace, or admin picks manually → **auto-
   compute**.
4. Whether it should count toward Hours Worked/OT - yes (requires a new
   write into `employee_shifts`, flagged up front as a table only the
   Kiosk app had ever written to) vs. no (just display the time) → **yes**.

## Design decisions not already covered by the AskUserQuestion answers
- **Reuse `get_effective_kiosk_settings`, not raw `kiosk_settings`.** This
  is what makes a Special Day override apply automatically to a manually
  entered time - the admin-panel side needed zero special-day-specific
  code as a result, it just passes the date through.
- **An admin correction always overwrites.** Chosen deliberately
  asymmetric to the kiosk RPCs' own `ON CONFLICT` (which only updates
  `status`, never the original check-in) - this function exists
  specifically *to* correct a wrong or missing time, so "always wins" is
  the right default for it, unlike a kiosk re-punch which shouldn't
  retroactively rewrite the first arrival time of the day.
- **Correct the earliest shift row, not every row.** Mirrors
  `record_face_punch`'s own `v_is_first` concept (lateness is only ever
  judged against the first punch of the day). A day with multiple real
  kiosk shifts already on it is a rare edge case this doesn't specially
  handle - the earliest one gets corrected, the rest are left alone.
- **No fabricated check-out, and no reliance on `auto_close_open_shifts()`
  to supply one later.** Two independent reasons found during research,
  both worth recording: (1) `TODO.md` REQ-FEAT-006 already flags that
  job's `pg_cron` schedule as possibly never actually applied live: an
  unverified dependency, not something to silently lean on; (2) even if it
  were scheduled, its own `UPDATE ... SET check_out_at = now()` stamps
  *today's* wall-clock time onto the open shift regardless of the shift's
  own date - fine for a same-day forgotten punch-out, but it would
  silently fabricate a multi-day-spanning shift duration for a shift
  opened by a manual check-in on a past date. `STAFF_SHIFT_BACKLOG_REVIEW.sql`
  documents this exact failure mode already occurring for real stale
  shifts - no reason to design a new feature that reintroduces it.
