## Design decisions not already covered by the AskUserQuestion answers
- **No in-grid delete/clear.** Cycling (P→A→L→P) and direct typing (P/A/L)
  never produce an "unmarked" state — only the existing confirm-dialog
  delete (Daily/Per-Employee views, unchanged) removes a record outright.
  Chosen so a fast run of keystrokes while editing a row can't accidentally
  wipe a day's record.
- **Roster = employees with at least one attendance row in the selected
  month**, not the full employee list. Matches the existing Daily/
  Per-Employee views' behavior (both are also sourced from
  `dbStaffAttendance`, not the separate `dbEmployees` report dataset, which
  is shaped differently - `role`/`subject` fields, not
  `designation`/`department`) - not a new limitation introduced by this
  change.
- **No working-day/holiday gating.** Only future dates (`> todayStr`) are
  disabled. Sundays/holidays stay editable, consistent with how the
  Employee module's existing single-day Mark Attendance tab already has no
  such gate (there is also no established "holiday calendar applies to
  staff too" concept anywhere in the staff-attendance code paths, so
  inventing one here would have been scope creep beyond what was asked).
- Future-date cells are kept **focusable but inert** (not `disabled`) so
  keyboard arrow navigation can move across them without desyncing which
  DOM node actually holds focus (a `disabled` button can't receive
  `.focus()`, which would have frozen arrow-key navigation at the first
  future-date column).
- Table uses `border-separate`/`border-spacing-0` rather than
  `border-collapse` - required for `position: sticky` header row + sticky
  first column to render correctly together across browsers.

## Design decisions not already covered by the AskUserQuestion answers
- **Reuse `get_effective_kiosk_settings`, not raw `kiosk_settings`.** This
  is what makes a Special Day override apply automatically to a manually
  entered time - the admin-panel side needed zero special-day-specific
  code as a result, it just passes the date through.
- **An admin correction always overwrites.** Chosen deliberately
  asymmetric to the kiosk RPCs' own `ON CONFLICT` (which only updates
  `status`, never the original check-in) - this function exists
  specifically *to* correct a wrong or missing time, so "always wins" is
  the right default for it, unlike a kiosk re-punch which shouldn't
  retroactively rewrite the first arrival time of the day.
- **Correct the earliest shift row, not every row.** Mirrors
  `record_face_punch`'s own `v_is_first` concept (lateness is only ever
  judged against the first punch of the day). A day with multiple real
  kiosk shifts already on it is a rare edge case this doesn't specially
  handle - the earliest one gets corrected, the rest are left alone.
- **No fabricated check-out, and no reliance on `auto_close_open_shifts()`
  to supply one later.** Two independent reasons found during research,
  both worth recording: (1) `TODO.md` REQ-FEAT-006 already flags that
  job's `pg_cron` schedule as possibly never actually applied live: an
  unverified dependency, not something to silently lean on; (2) even if it
  were scheduled, its own `UPDATE ... SET check_out_at = now()` stamps
  *today's* wall-clock time onto the open shift regardless of the shift's
  own date - fine for a same-day forgotten punch-out, but it would
  silently fabricate a multi-day-spanning shift duration for a shift
  opened by a manual check-in on a past date. `STAFF_SHIFT_BACKLOG_REVIEW.sql`
  documents this exact failure mode already occurring for real stale
  shifts - no reason to design a new feature that reintroduces it.

## Bugs found live, root-caused via Supabase MCP `execute_sql`, fixed via `apply_migration`
All three surfaced only once a real Save actually ran against the real
schema - `npm run lint`/dev-server compiling cleanly, and even the earlier
Supabase MCP pre-flight checks (which only confirmed the two objects the
function *calls* exist, not the full constraint shape of the tables it
*writes*), couldn't have caught any of them statically:

1. **`employee_attendance_punch_method_check` violation.** First real
   double-click-and-save attempt returned `new row for relation
   "employee_attendance" violates check constraint
   "employee_attendance_punch_method_check"`. Queried
   `pg_get_constraintdef` - `CHECK (punch_method = ANY
   ('face','code','qr'))`, no `'manual'` value ever allowed. Fixed:
   `CREATE OR REPLACE FUNCTION admin_set_manual_checkin(...)` re-applied
   (migration `admin_set_manual_checkin_fix_punch_method`) using `NULL`
   instead of `'manual'` for `punch_method` - this file's own header
   comment already documented NULL as the pre-existing "admin-set, not
   kiosk" signal (mirroring `staffLeaveService.js`'s own comment), so this
   was correcting an oversight against the project's own stated
   convention, not inventing a new rule.
2. **`employee_shifts` NOT NULL violation.** Retried Save, new error:
   `null value in column "punch_method" of relation "employee_shifts"
   violates not-null constraint`. Queried
   `information_schema.columns` - `is_nullable: 'NO'`,
   `column_default: 'face'`. Fixed: `ALTER TABLE employee_shifts ALTER
   COLUMN punch_method DROP NOT NULL` (migration
   `employee_shifts_punch_method_nullable`) - the existing CHECK already
   tolerates NULL per standard SQL semantics (a CHECK only fails on
   FALSE, never on NULL/unknown), so no further constraint change was
   needed.
3. **`idx_employee_shifts_one_open` unique violation.** Retried again,
   new error: `duplicate key value violates unique constraint
   "idx_employee_shifts_one_open"`. Queried `pg_indexes` -
   `CREATE UNIQUE INDEX ... ON employee_shifts (employee_id) WHERE
   (check_out_at IS NULL)` - one open shift per employee **globally**,
   not per date. The test employee already had an unrelated real open
   shift elsewhere, so the function's "insert a new open shift when none
   exists for this date" fallback collided with it. Recognized this is a
   design flaw beyond just the constraint: an open-ended shift means
   "still clocked in right now," which is false for a backdated
   correction regardless of whether the index happens to catch it for a
   given employee. Fixed by deleting the INSERT branch outright - the
   function now only ever `UPDATE`s an existing `employee_shifts` row,
   never creates one. Re-applied as migration
   `admin_set_manual_checkin_no_open_shift_insert`. Updated both the
   `.sql` file's header comment and its inline comment to document this
   narrower (but correct) behavior.

## Schema

## New DB function - supersedes REQ-FEAT-011's write path entirely
`mobile-app/SUPABASE_ADMIN_ATTENDANCE_CELL.sql`:
- `admin_save_attendance_cell(p_employee_id, p_date, p_status,
  p_check_in_at DEFAULT NULL, p_is_informed DEFAULT NULL, p_reason DEFAULT
  NULL) RETURNS TABLE(o_is_late, o_late_minutes)`. Validates `p_date` isn't
  future and `p_status IN ('P','A','L')`. When `p_status = 'P'` and a
  check-in time is given, computes lateness via
  `get_effective_kiosk_settings(p_date)` exactly as
  `admin_set_manual_checkin` did (Special Day awareness comes for free,
  zero special-day-specific code in this function). Upserts
  `employee_attendance` with an authoritative `DO UPDATE SET` (always
  overwrites) - `is_informed`/`reason` are only set when `p_status IN
  ('A','L')`, left NULL otherwise; `check_in_at`/`is_late`/`late_minutes`
  are only set when Present, NULL otherwise - switching a day's status
  cleanly clears whichever half no longer applies. Corrects the day's
  earliest `employee_shifts` row's check-in **only if one already
  exists** (same UPDATE-only reasoning as REQ-FEAT-011 -
  `idx_employee_shifts_one_open` and the "an open shift means still
  clocked in right now" semantics problem, unchanged from before).
- `DROP FUNCTION IF EXISTS admin_set_manual_checkin(...)` - removed as
  dead API surface rather than left unused.
- `list_kiosk_special_days_in_range(p_from, p_to)` - read-only,
  `SECURITY DEFINER` (the table is `REVOKE ALL FROM anon, authenticated`),
  granted to `authenticated`. `list_kiosk_special_days()`
  (`SUPABASE_KIOSK_SPECIAL_DAY.sql`) only returns `date >= today`
  (built for the Settings page's own "what's upcoming" need) - the Grid
  also needs *past* Special Days for a month already gone by, so this adds
  the range form without touching the original at all.

## Design decisions not already covered by the AskUserQuestion answers
- **Status switch clears the other half's fields rather than leaving stale
  data behind.** Verified live: Absent→Present correctly nulled
  `is_informed`/`reason` in the same write (not merely hidden in the UI).
  Chosen because a day can't simultaneously be "Present at 8:15" and
  "Absent, informed, called in sick" - keeping both sets of fields
  populated at once would be actively misleading data, not just untidy.
- **Enter/Space left unhandled in the cell's own `onKeyDown`.** A native
  `<button>` already activates (fires `onClick`) on either key - handling
  them explicitly would have meant either duplicating `handleCellClick`'s
  logic or fighting the browser's own default behavior for no benefit.

## Live bugs found and fixed (same real-employee testing pattern as REQ-FEAT-011)
1. **Copy/paste wrote the wrong date.** `Ctrl+C` on a Present+08:15 cell
   (date 2026-10-04) then `Ctrl+V` onto 2026-10-05 was *intended* to write
   an 08:15 check-in on the 5th. First attempt: queried
   `employee_attendance` for both dates afterward - only the 4th existed;
   nothing was written for the 5th at all (see the focus-restore bug
   below, which was the actual cause of that particular symptom). Root
   cause of the *date* bug itself, found while reading the paste code to
   debug the missing-write symptom: `clipboardRef.current = {...val}`
   captured the cell's full ISO `checkIn` timestamp (e.g.
   `"2026-10-04T08:15:00+05:30"`), and the paste loop passed that same ISO
   straight through regardless of which target date `d` it was pasting
   onto - so a successful paste onto the 5th would have silently written
   the *4th's* date into the 5th's `check_in_at`. Fixed: clipboard now
   stores `checkInTime` (bare `"HH:MM"`, via the existing
   `toTimeInputValue()`) instead of a raw ISO string; the paste loop
   rebuilds `` `${d}T${checkInTime}:00+05:30` `` per target date `d`,
   identical to how `saveEditor()` itself builds the ISO from a typed
   time. Verified after the fix via direct SQL:
   `2026-10-05 check_in_at = '2026-10-05 02:45:00+00'` (08:15 IST on the
   *5th*, not the 4th it was copied from).
2. **Focus wasn't restored after closing the editor - this was the actual
   cause of bug 1's "paste did nothing" symptom.** Sequence that exposed
   it: open a cell's editor (click), click Cancel, then Ctrl+C → ArrowRight
   → Ctrl+V with no DOM focus ever having returned to a grid cell button.
   None of those keyboard events had anywhere real to land - `Ctrl+C`
   silently captured nothing into `clipboardRef`, `ArrowRight`'s
   `handleKeyDown` never fired, `Ctrl+V` did nothing - and the UI gave no
   visible error, so the first signal this had happened at all was the
   direct-SQL check coming back with the target date simply absent rather
   than wrong. Root cause: `onClick={() => { setEditCell(null);
   setEditForm(null); }}` on Cancel and the backdrop, and the same inline
   pattern on a successful Save, all cleared editor state without ever
   calling `.focus()` on the cell button the editor had opened from -
   browser focus was left on whatever DOM node was actually clicked
   (the Cancel button), not restored anywhere once that button's parent
   modal unmounted. Fixed with a single `closeEditor()` function that
   captures `editCell` before clearing it, then calls the existing
   `focusCellAt(cell.row, cell.col)` - wired into Cancel, the backdrop
   `onClick`, and `saveEditor()`'s success path, replacing all three
   inline `setEditCell(null); setEditForm(null);` pairs.

## Schema drift found while reading the live function (before touching anything)
`pg_get_functiondef('save_kiosk_special_day'::regproc)` showed the live
body already differs from `SUPABASE_KIOSK_SPECIAL_DAY.sql`'s original:

- Gained `PERFORM recompute_late_arrivals_for_date(p_date::DATE);` at the

## Why backdating is safe - checked before relying on it
Read `recompute_late_arrivals_for_date(p_date)`'s definition: loops
`employee_shifts` rows for that date with a non-null `is_late`,
recalculates `is_late`/`late_minutes` against
`get_effective_kiosk_settings(p_date)`, writes the result into both
`employee_shifts` and `employee_attendance`. Since this already runs at
the end of both save and delete, and already applied to future-dated
Special Day changes before this migration, removing the past-date guard
doesn't introduce any new staleness risk - it just lets the same
already-correct mechanism also apply to past dates.
