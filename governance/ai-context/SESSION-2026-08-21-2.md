## Objective
"check RLS on students and employees tables" — a direct follow-up to the
credentials-scan thread in Part 1, which only checked tracked *files* for
secrets. This is a different, deeper question: whether the database's own
access-control layer (RLS) actually enforces anything, which files alone
can't answer.

## What was checked, and how

### File-level research first
Grepped `admin-panel/database/schema.sql` for any `ENABLE`/`DISABLE ROW
LEVEL SECURITY` or `CREATE POLICY` statement — **zero matches**. RLS
enable/policy statements for `students`/`employees` aren't in any tracked
schema file at all (consistent with `documentation\PROJECT_CONTEXT.md`'s
existing note that `admin_users` has no `CREATE TABLE` in-repo either —
whatever RLS setup exists on these tables was done ad hoc in the Supabase
dashboard, never scripted).

Found `mobile-app/SUPABASE_SETUP.sql:110-118` does define narrower
policies: `students_own_profile`/`employees_own_profile`, both
`FOR SELECT USING (app_user_id = auth.uid())`. On paper this reads as
locked-down (only a user's own row, matched by Supabase Auth's `auth.uid()`).
But per this project's own already-documented finding
(`documentation\PROJECT_CONTEXT.md`), mobile auth never creates a real
Supabase Auth session — it's custom `teacher_login`/`student_login` RPCs
checking `app_password` directly — so `auth.uid()` is never populated for
mobile users at all. A policy keyed on it, alone, would functionally lock
the table to *everyone*, not open it to anyone. That mismatch (policy
implies "locked", but the earlier `BOOTSTRAP.md` framing assumed "stale but
still enabled, effectively locked") is what made a live test necessary
instead of trusting the file read.

### Live test (the actual answer)
Also found `mobile-app/SUPABASE_SECURITY_AUDIT.sql` already exists —
written specifically to answer this via 4 queries (RLS on/off per table,
anon/authenticated grants, existing policies, sensitive-column check) — but
it has to be run in the Supabase SQL Editor or with DB/service-role
credentials, neither of which exist in this repo or session. Did not search
for or attempt to obtain either (would be exactly the credential-hunting
this session's own Part 1 thread already had correctly blocked once).

Instead, wrote a throwaway script (`admin-panel/_rls_check_tmp.mjs`,
deleted immediately after use, never committed) using the project's own
already-installed `@supabase/supabase-js`, `NEXT_PUBLIC_SUPABASE_URL`/
`NEXT_PUBLIC_SUPABASE_ANON_KEY` from `admin-panel/.env.local` (the app's own
public runtime config — the same anon key already embedded in the deployed
client bundle, not a discovered secret), `persistSession: false` (fresh,
unauthenticated client, no login attempted). Queried:
```js
supabase.from("students").select("id, first_name, last_name, app_password, mobile1", { count: "exact" }).limit(3)
supabase.from("employees").select("id, name, app_password, phone", { count: "exact" }).limit(3)
supabase.from("admin_users").select("*", { count: "exact" }).limit(3)
```

**Result — all three returned full data, zero authentication:**
| Table | HTTP status | Rows returned (of total) |
|---|---|---|
| `students` | 206 (partial content — normal for `.limit()`) | 3 of 48 |
| `employees` | 206 | 3 of 27 |
| `admin_users` | 206 | 3 of 4 |

Sample `students` row included `app_password` as plaintext (the shared
default value already on record elsewhere in this doc set, not restated
here per existing project convention — see `SECURITY-THREAT-MODEL.md` F1).
Same for `employees`. `admin_users` returned `id`, `name`, `initials`,
`role` for real admin accounts — not previously flagged as its own
exposure; it's outside the `mobile-app/SUPABASE_*.sql` grep that scoped the
"~25 tables" figure in REQ-SEC-002 (it's a core/dashboard-created table).

## Conclusion
RLS is not effectively protecting `students`, `employees`, or `admin_users`
against anonymous access, live, right now. Given the file evidence (an
`auth.uid()`-only policy exists, which should functionally block everyone
since mobile never sets `auth.uid()`) contradicts the live result (wide
open to everyone), one of these is true and can't be distinguished without
running the audit SQL in the dashboard:
- RLS is disabled entirely on these two tables (or was never enabled to
  begin with — no tracked `ENABLE ROW LEVEL SECURITY` statement exists for
  them anywhere), or
- An older, broader permissive policy predates this repo's SQL-file
  history (never captured in any migration file) and is still active,
  OR-ing in full access regardless of the newer narrow policy.

Either way, the practical exposure is identical: full anonymous read access
to both core PII tables and the admin roster.
