## Addendum 6 (same session) — Phase 1.7: cost/privacy safety rails

User: "if many users log will come does it take lot space in database and
server? exceeding free limit?" Rather than answer from general knowledge
of Supabase's published tiers (which drift and I can't verify live),
queried the actual project via the Supabase MCP connection already
available in this session (`mcp__supabase__execute_sql`):
`pg_database_size(current_database())` → 19 MB total;
`pg_stat_user_tables` → `diagnostic_reports` didn't exist yet (migration
still not applied), biggest existing table (`student_attendance`, ~4,000
rows) ~200 bytes/row. Concluded storage size was never the real risk —
single-entry auto-submitted rows are small; the actual gap was that
nothing throttled a repeating error, so a loop or a bug hitting every
page load could fire unboundedly regardless of user count. Proposed a
fix (throttle + retention) and asked before implementing, since it
touches the same shipped feature again.

User replied in one message: "fix and keep enable and disable logging
because logging is specifically kept for development purpose not to
collect what users do" — approval to implement the fix, plus a materially
new requirement (a kill switch) that reframes the feature's default
posture from always-on to opt-in. Treated as clear enough direction to
implement directly (§J12B PATCH-level continuation of the same session's
feature, not a new architecture needing another plan-and-confirm round),
while making every design choice explicit in this log so it can be
corrected if misread.

**Key design decision, reasoned through before coding:** does the
enable/disable switch gate local buffer/file capture too, or only the
Supabase submission? Decided: only the Supabase submission. Local
capture stays on-device always (needed for "Report a Problem" to have
context, and nothing about it is "collected" by anyone unless the user
chooses to send it). The switch specifically gates the thing that
constitutes "collecting what users do" in the sense the user meant —
automatic transmission to a place an admin can see. Manual "Report a
Problem" was excluded from the gate for the same reason in the other
direction: it's explicit per-incident consent, categorically different
from passive auto-capture, so it should work regardless of the switch.
Default state: OFF (matches "kept for development purpose" — opt-in when
actively debugging, not always-on).

**Implemented:**
- Extended `mobile-app/SUPABASE_DIAGNOSTIC_REPORTS.sql` (still not
  applied to production) with `diagnostic_settings` (single row,
  `enabled boolean default false`), RLS mirroring `diagnostic_reports`'
  `is_admin_user()` pattern (anon+authenticated SELECT, admin-only
  UPDATE), plus a DELETE policy on `diagnostic_reports` itself (needed
  for the retention cleanup below) — **caught and fixed a mistake
  immediately**: the first edit accidentally dropped the existing
  `WITH CHECK (public.is_admin_user())` clause from the UPDATE policy
  while inserting the new DELETE policy between two existing ones;
  re-read the file after editing and caught it before moving on.
- `admin-panel/src/lib/logger.js` — added `AUTO_SUBMIT_COOLDOWN_MS`
  (5 min) + `AUTO_SUBMIT_SESSION_CAP` (20), a `diagnosticsEnabled`
  module-level flag (default false) + `refreshEnabledFlag()` (exported,
  called once from `DiagnosticsInit.jsx`'s mount effect), and a new
  `isEnabled()` helper inside `submitReport` that uses the cached flag

  API-route errors run in Vercel's serverless model with no long-lived
  process to cache a client-fetched flag in, so caching would either
  never populate (my first draft's bug, caught before shipping — see
  below) or go stale; a live read per server-side error occurrence is
  fine since those are rare.
  - **Caught a real design bug in my own first draft**: I initially

    working forever, a real regression from the working Phase 1.6
    behavior. Caught this by re-reading the file's own logic before
    running lint, not by tooling (lint/analyze can't catch "this

- `mobile-app/lib/core/utils/diagnostic_logger.dart` — added the same
