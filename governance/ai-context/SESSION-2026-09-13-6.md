## Result: the kiosk face-scan freeze is FIXED and CONFIRMED

Ran two separate scan sessions, one lasting ~13 minutes (178 poll ticks),
with the camera never needing to reinitialize and zero skipped/re-entrant
polls in either run.

### The core metric: idle "no-face" cycle time

| | Before (takePicture) | After (live stream) |
|---|---|---|
| Typical cycle | 4,500-7,400ms | 22-400ms |
| First cycle after camera init (JIT warm-up) | ~4,300-5,700ms | 399ms |
| Steady-state | ~5,500-6,900ms | 22-60ms |

That is roughly a **100-300x reduction** in the time each idle poll takes.
This is the number that maps directly to the reported symptom ("camera
freezing, restarting again and again") — nobody standing at the kiosk now
waits multiple seconds between the app trying to notice them; it happens
close to every second, as designed.

### Rotation/mirror correctness - the single biggest risk in `-5`'s work

Confirmed correct via two independent live face detections:

- `FACE box=100x132` and `FACE box=158x205` - both **taller than wide**,
  the expected aspect ratio for an upright face crop. A rotation error
  would show up here first (a sideways face crop is roughly as wide as
  tall, or wider).
- Two live match attempts against the real enrolled staff database scored
  **0.581** and **0.601** similarity (`kMatchThreshold = 0.6`). Neither
  matched - the first was below threshold, the second cleared the
  threshold but missed the required 0.05 distinctiveness margin against
  the second-best candidate (0.601 vs 0.557, margin 0.044). Both are
  strong, non-degenerate signal: a badly wrong rotation or mirror
  convention would be expected to produce near-random, much lower
  similarity (typically 0.0-0.3 for a garbled crop), not two independent
  attempts landing close to the actual decision boundary. Not chasing an
  actual confirmed match further this session - the native-confirm-dialog
  → record-punch path downstream of a match is unchanged code, already
  verified working in `SESSION-2026-09-13-3.md` against the JPEG capture
  path; today's new code (stream capture, NV21 conversion, rotation) is
  what needed verifying, and it now has been.

### Everything else observed

- `STEP startImageStream ok in 1ms` - stream starts essentially instantly.
- `sensorOrientation=0 rotation=0 mirror=true` logged at camera init on
  this device - BlueStacks' virtual camera reports a 0° sensor orientation
  (plausible for a webcam passthrough with no real sensor rotation),
  giving `_rotationDegrees = 0` via the front-camera formula. Untested:
  whether a real device's front camera (typically sensorOrientation 90 or
  270) produces an equally correct rotation - the formula is standard and
  the geometry evidence above is reassuring, but this specific value
  wasn't exercised on this hardware. Worth a first-real-scan sanity check
  (a colleague or the user trying it) rather than assuming.
- `nv21ToImage` conversion cost: 14-73ms - cheap, and (as designed) only
  paid once a face is actually detected, not on every poll.
- One 432ms main-isolate stall recorded across both runs (not zero, but
  nowhere near the old recurring multi-second pattern) - plausibly TFLite
  JIT/GC during the first live liveness+embedding run, consistent with
  what `-3` observed on the old path too.

## New finding: Supabase embeddings fetch is itself slow (~5.8-6.2s)

Both live match attempts showed the SAME shape: every camera/ML-Kit/TFLite
stage fast (all under 100ms individually), then a `MATCH` log line
5.8-6.2 SECONDS after `getEmbedding` finished. That gap is
`SupabaseService.fetchAllFaceEmbeddings()` - a plain network round-trip,
completely unrelated to anything this thread has touched. It was always
there in the original code; it just used to be masked by `takePicture()`'s
own comparable-magnitude delay, so nobody could previously tell the two
apart.

**This is NOT part of the reported bug and was not fixed or touched this
session.** It only affects the brief window AFTER a face is actually
detected and verified (the "Verifying..." spinner state) - a real but much
less severe UX cost than an unresponsive idle camera, and arguably was
already present and tolerable enough that it was never separately
reported. Flagging it plainly rather than either fixing it unasked or
staying silent about a real finding.
