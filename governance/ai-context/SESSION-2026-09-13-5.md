## Investigation this session

### Candidate: lock focus/exposure once at camera start

Theory: CameraX's `ImageCapture` may wait for auto-focus/auto-exposure
convergence before each still capture; locking once avoids re-negotiating
per shot. Implemented `controller.setFocusMode(FocusMode.locked)` /
`setExposureMode(ExposureMode.locked)` in `face_punch_page.dart`, wrapped
defensively (see below).

**First result: crashed camera init entirely.** On BlueStacks' camera,
`setFocusMode(locked)` threw `CameraException(IllegalArgumentException,
"None of the specified AF/AE/AWB MeteringPoints is supported on this
camera")` — not caught, so the whole `_initCamera()` try/catch treated it
as total camera failure, going straight to the error screen with a
completely unusable scan screen. **This is a real, not hypothetical, risk
for whatever the physical kiosk tablet's front camera turns out to
support too.** Fixed by wrapping the lock attempt in its own try/catch that
logs and falls back to default auto focus/exposure on failure, rather than
taking down the entire camera. Verified this fallback works cleanly across
two camera generations (a mid-run reinit happened, unexplained — see
"Loose end" below — and both generations degraded gracefully).

**Because locking failed on BlueStacks, this environment couldn't test
whether locking actually helps** — it silently fell back to auto both
times, so `takePicture()` timing was unchanged (5.8-5.9s), but that's not
evidence either way, just an untested environment gap.

### Candidate: swap the native Android camera engine (CameraX → legacy Camera2)

Added `camera_android: ^0.10.11+1` as a direct pubspec dependency —
confirmed compatible with the resolved `camera_platform_interface: 2.13.1`
and Flutter 3.47.4 via a `pub.dev` API check first. This overrides the
`camera` plugin's own default (`camera_android_camerax`) per Flutter's
federated-plugin resolution rules. `flutter pub get` confirmed via
`.flutter-plugins-dependencies` that `camera_android` (legacy Camera2) was
now the only Android implementation resolved.

**Result: measurably WORSE, not better.** On the legacy engine,
`setFocusMode(locked)`/`setExposureMode(locked)` **succeeded** this time
(no exception) — meaning this candidate finally got a real, valid test of
the lock theory. `takePicture()` was measured at 4572, 7267, 7380, 6522,
6703, 6906, 6482ms across 7 calls (avg ~6.5s) — worse than CameraX's
~5.5s average, **even with focus/exposure genuinely locked**. This
conclusively disproves the 3A-convergence-wait theory generally (locking
succeeded, made no difference) and rules out the camera engine as the
lever (legacy was worse). Also observed the legacy engine rendered the
live preview visibly rotated ~90° — a real regression that would have
needed its own fix had this path been kept.

**Reverted**: removed `camera_android` from `pubspec.yaml`, ran
`flutter pub get` again, confirmed `.flutter-plugins-dependencies` shows
`camera_android_camerax` restored.

## Conclusion from three ruled-out theories

| Theory | Result |
|---|---|
| Flash mode auto → off (session -4) | No change (~5.5s either way) |
| 3A focus/exposure lock | No change even when lock succeeded (~4.5-7.4s) |
| Legacy Camera2 engine instead of CameraX | Worse (~6.5s avg) + broken preview rotation |

All three are settings/engine-choice tweaks to the SAME underlying
operation: "capture a full-quality still photo." None moved the number.
This is strong evidence the delay is inherent to that operation itself on
this camera (real or virtualized), not to any configuration of it —
matching the user's own confirmation that real hardware behaves the same
as BlueStacks.

**Explicitly confirmed with the user before proceeding**: presented this
evidence and asked whether to attempt the one remaining lever that
structurally avoids the slow operation entirely — replacing `takePicture()`
with reading frames from the camera's live preview stream instead, a
materially bigger change touching code the original design explicitly
avoided for reliability reasons (see `face_recognition_service.dart`'s
original header comment, now rewritten). **User said yes, proceed.**

## The rewrite: live camera stream instead of takePicture()

### Design

Kept the existing, already-verified `_scheduleNextPoll` one-shot timer
cadence (armed ~1s after the previous attempt fully finishes) completely
unchanged — this is a minimal, surgical swap of WHERE the frame comes from,
not a rewrite of the polling/scheduling logic that was already proven
correct in `-2`/`-3`.

- `CameraController` now requests `imageFormatGroup: ImageFormatGroup.nv21`.
  Confirmed via reading `camera_android_camerax`'s own Java source
  (`ImageProxyUtils.planesToNV21`) that on Android this hands back a single,
  already-destrided NV21 buffer — not raw 3-plane `YUV_420_888` with
  sensor-specific row padding to handle manually. This is also the exact
  format ML Kit's `InputImage.fromBytes` expects on Android, so one setting
  serves both needs.
- `controller.startImageStream((image) => _latestFrame = image)` runs
  continuously from camera init; each poll just reads whatever `_latestFrame`
  currently holds — a plain field access, not an async native call, so the
  old "controller changed mid-capture" race (which existed specifically
  because `takePicture()` was an awaited call spanning a possible controller
  swap) no longer applies.
- `FaceRecognitionService` gained `nv21ToImage()` (NV21 → RGB `img.Image`,
  standard BT.601 conversion, then `img.copyRotate` + optional
  `img.flipHorizontal`) and `detectFaceFromInputImage()` (ML Kit run
  directly on bytes, no exposure-corrected-copy trick — that trick writes a
  temporary JPEG for ML Kit to re-read, which only makes sense for the
  file-based enrollment path).
- **Rotation/mirror computed ONCE per camera generation**, not per frame —
  the kiosk is bolted down in a fixed portrait orientation (confirmed by
  every screenshot taken across this whole thread), so unlike a handheld
  app this doesn't need to track live device-rotation changes. Formula
  matches the standard one used in Google's own ML Kit example apps:
  front-facing sensors are mirrored, so `rotationDegrees = (360 -
  sensorOrientation) % 360`; back camera would use `sensorOrientation`
  directly (dead code path here — kiosk always tries front first).
- **Performance detail**: the NV21→RGB conversion (`nv21ToImage`, a real
  pixel-loop cost) only runs once ML Kit has confirmed a face is present in
  the raw bytes — not on every poll. Most polls (nobody standing at the
  kiosk) now do strictly less work than before, not just faster work.
- Removed the focus/exposure-lock attempt from `_initCamera` entirely
  (dead weight now — it targeted a takePicture()-specific mechanism this
  rewrite no longer uses, and its real cost, exposure not adapting to
  changing daylight, no longer has any offsetting benefit). Kept
  `setFlashMode(off)` (trivial, harmless, front camera has no flash
  hardware regardless of capture mechanism).
- `_reinitCamera` now also attempts `stopImageStream()` (best-effort,
  wrapped) before disposing the old controller.

## Loose end (not investigated, low priority)

During the focus/exposure-lock defensive-fallback verification, a
`CAMERA reinit requested` fired ~9.8s into a run with no deliberate button
press from this session's testing. Plausibly a delayed/duplicate `adb
shell input tap` event landing on the error screen's "Try Again" once the
page had already transitioned (this session tapped the same screen
coordinates twice in quick succession while working around a slow cold
start) rather than an app defect — the app handled it gracefully either way
(clean reinit, gen2 came up fine, no stuck state). Not reproduced
deliberately, not chased further; flagging in case it recurs.
