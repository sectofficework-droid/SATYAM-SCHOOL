## Permanent fix: phase_number now fills gaps instead of only climbing
User's next message made clear the one-off renumber above wasn't enough -
they wanted the underlying assignment rule changed: "make sure if any
batch deleted then next batch should continue from where it is not
used not like a unique number we are not giving enrollment number here."
In other words: `phase_number` is a display counter, not meant to behave
like the permanent, never-reused enrollment numbers elsewhere in this
schema - deleting a batch should free its number for reuse.

Shipped `mobile-app/SUPABASE_PHASE_NUMBER_GAP_FILL.sql`: replaced the
column's `nextval('student_import_phases_phase_number_seq')` default with
a new `next_student_import_phase_number()` PL/pgSQL function that scans
`generate_series(1, max(phase_number)+1)` and returns the smallest value
not already present - the classic "first gap" (MEX) query. Added
`pg_advisory_xact_lock(hashtext(...))` inside it so two near-simultaneous
batch creations can't both compute the same gap before either commits
(the `UNIQUE(phase_number)` constraint would otherwise fail the second
one) - cheap, and the only part of this that needed any real thought.
Confirmed via `pg_constraint` that `phase_number` is UNIQUE and NOT
referenced as a foreign key anywhere else in the schema (only `id`/
`phase_id` joins exist), so neither the column type nor any other table
needed touching - purely a default-expression swap.

**No application code changed** - every insert call site
(`recordPhase()`, `createEmptyBatch()`) already omits `phase_number`
entirely, relying on the column default, so the new behavior takes effect
automatically everywhere batches get created.

**Verified live** directly against the real table (not a scratch/test
table - there is no staging environment for this schema): inserted a
throwaway row with `source: 'test_gap_fill'`, confirmed it got
`phase_number: 7` (correctly continuing after 1-6); deleted it; inserted
a second throwaway row and confirmed it got `7` again - direct proof the
freed number is reused, not skipped. Deleted that row too. Final state
re-verified: exactly batches 1-6, in order, nothing extra left over.

## Bug fix: StudentNoteBadge popover clipped on Student list + Government Entry
User: "note in the government docuemnt section and student management
section not behaving well and where is note saving button?" Root-caused
before touching code: `StudentNoteBadge`'s popover was a CSS
`position: absolute` child positioned relative to its own `relative`
wrapper, which worked fine on the Documents page (tested only on row 1,
with ample room below) but sits inside, on the Student list page, each
student card's `rounded-2xl ... overflow-hidden` wrapper
(`student/page.js:1378`), and on Government Entry, the frozen-column table
inside a `overflow-auto rounded-xl ...` scroll container
(`government-entry/page.js:4805`). Either ancestor clips any
absolutely-positioned descendant that would render outside its bounds -
confirmed both via `Grep` before concluding this was the cause, not
guessed. Depending on which row/card was clicked, the popover's lower
portion (frequently the Save button) rendered outside the visible,
clipped area - explaining both complaints ("not behaving well" and "where
is note saving button") as the same underlying bug.

**Fix**: rewrote `StudentNoteBadge.jsx` to render its popover (and
backdrop) through `createPortal(..., document.body)` instead of a
CSS-relative wrapper, positioned with `position: fixed` computed from the
trigger button's own `getBoundingClientRect()` at open time - this
escapes any ancestor's `overflow` clipping regardless of which page
mounts it, since the DOM node is no longer nested inside that ancestor at
all. Added simple edge-avoidance: clamps horizontally to stay within the
viewport, and flips to render *above* the trigger instead of below when
there isn't ~280px of room underneath (verified this triggered correctly
on Government Entry's UDISE tab, row 269 near the bottom of a long
scrolled table).

**Second finding while fixing this**: because React portals bubble
synthetic events through the *React* component tree, not the DOM tree, a
click anywhere inside the portaled popover - or on its full-screen
backdrop - would otherwise still bubble up to whatever onClick a parent
component had (the Student list card's whole-card `onClick` navigator,
specifically). This risk existed in the *pre-portal* version too (the
backdrop was a plain, non-portaled sibling, so normal DOM bubbling had the
same effect) - just never surfaced because nobody had tried clicking
outside the note popover on that page yet. Fixed by adding
`e.stopPropagation()` to both the backdrop's and the button's own
`onClick`, on top of the panel's existing stopPropagation.

Removed the now-unused `align` prop (positioning is automatic now) from
the one call site that passed it (`StudentDocumentsSection.jsx`'s NOTE
column).

**Verified live**, post-login (the admin session had timed out mid-session
from inactivity - had the user log back in rather than guessing or using
