## Decisions
1. **Tier 1 only, no DDL.** Half-day status and leave types both need schema changes to
   a live `CHECK` constraint / table. Not approved for this change, so recorded in
   `TODO.md` instead (§J9 scope control). No migration written or run.
2. **`STANDARD_DAY_HOURS = 8` as a module constant**, not a `kiosk_settings` column.
   A column would need a migration plus an admin save path for a value this project
   has never had. The `shift_end_time` (16:00) is a *cutoff*, not a shift length —
   deliberately not reused as the OT baseline.
3. **OT sums signed per-day balances**, not `totalHours - 8*days`. Summing balances
   keeps a 6-hour day from silently cancelling a 10-hour day inside the same period,
   which is what an OT dispute is actually about. Verified by test.
4. **Rollup is applied to the already-filtered day rows**, not to the raw source. So the
   date range and every quick filter narrow the per-employee view too. The rollup
   config's `getData` is deliberately a no-op — re-filtering per-employee rows would
   double-apply filters that no longer have a meaning there (a "Present" filter against
   a count of 5).
5. **Working days is a user-facing filter** (All / Exclude Sundays / Exclude weekends)
   rather than a hardcoded policy. Reusing the student `holidays` table was **not**
   done — it is a student-scope calendar and reusing it for staff needs its own
   decision. Recorded as a follow-up.
6. **Weekday computed with an explicit local-time parse.** `new Date("2026-06-01")`
   parses as UTC midnight, which is the previous day in IST and would have put every
   Monday's attendance under Sunday. Caught deliberately; covered by a test.
7. **Empty ≠ zero** throughout: a day with no measured hours shows blank balance, not
   `0.0` shortfall. A period that nets to exactly zero *does* show `0.0` — blank would
   misread as "no hours worked". Caught by test after the first implementation got it
   wrong.

## Deviation from the presented plan (self-correction)
I first added date-range pushdown (`{ from, to }`) to `getStaffAttendanceForReport` for
the performance item. Reverted it: the report page loads **all** report types in one
`loadAll()` (`page.js:815`), so nothing ever calls it with arguments — it was dead code
(§K3). Left the no-arg signature. Performance is therefore **not** improved; the
pre-existing "loads every attendance row up front" behavior is unchanged and still open.

### Two data findings that change the earlier conclusions
1. **`employee_attendance` is EMPTY — 0 rows.** This was done deliberately in session 1
   (its own work-log records truncating it for testing). Consequence: the report I
   built reads from `employee_attendance`, so **it will render zero rows right now**
   and the new tiles/columns cannot be exercised until real punches accumulate. This
   is the most important thing for the user to know before looking at the UI.
2. **The 17 open shifts are orphans** — 0 matching `employee_attendance` day rows for
   all 17 staff across all 3 dates. So no day-level record references them, and my
   report's `unclosedShifts` column (which is computed per day-row) will never even
   see them. They surface in the *Employee → Who's In* view, not in this report.

### Why a blanket "close the stale shifts" cleanup is NOT safe
Modelling a close at 16:00 IST on each punch-in date produces **-101.7 hours net
shortfall** across the 17, and for three of them a **negative duration**, because
their punch-in was *after* 16:00 and the computed close would precede it:
- Debiprasad Das (EMP003) 2026-09-09 18:05 → -2.1 h
- Rudra Prasad Muni (EMP007) 2026-09-09 20:26 → -4.45 h
- Pragyan Panda (EMP024) 2026-09-17 20:04 → -4.08 h

These are almost certainly people who punched in late and then left the tablet
without checking out, not 20-hour shifts. Writing `check_out_at < check_in_at` would
be data corruption and would poison the new OT/shortfall column. **No cleanup was
executed.** A reviewed SQL script is prepared and left for the user to run — see the
next session entry.
