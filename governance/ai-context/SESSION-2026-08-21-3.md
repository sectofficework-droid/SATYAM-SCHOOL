## Implementation

### Database (`mobile-app/SUPABASE_HASH_APP_PASSWORD.sql`, new file)
1. `CREATE EXTENSION IF NOT EXISTS pgcrypto`.
2. `_app_password_backup_20260821` table + inserts (idempotency guard:
   `WHERE app_password NOT LIKE '$2%'`, so a re-run never backs up an
   already-hashed value).
3. `UPDATE ... SET app_password = crypt(app_password, gen_salt('bf'))` on
   both tables, same idempotency guard.
4. `teacher_login`/`student_login` redefined: compare via
   `app_password = crypt(p_password, app_password)`; return
   `(row_to_json(v_row)::jsonb - 'app_password')::json` instead of the
   whole row — stops shipping the (now-hashed, but still shouldn't leave
   the DB) password back to the client on every login, a related exposure
   noted in `SECURITY-THREAT-MODEL.md` F2 that was in scope here since it's
   the same two functions.
5. `teacher_change_password`/`teacher_verify_password` redefined the same
   way (compare + write via `crypt()`).
6. **New:** `student_alerts` table, mirrors `teacher_alerts` exactly
   (`id`, `student_id` FK `ON DELETE CASCADE`, `title`, `message`,
   `created_at`). `SELECT`-only grant to `anon` — deliberately narrower
   than `teacher_alerts`' legacy full grant, since nothing in the client
   ever writes to either table (noted as not replicating that over-grant,
   REQ-SEC-002).
7. **New:** `admin_reset_student_password(p_student_id, p_new_password)` /
   `admin_reset_employee_password(p_employee_id, p_new_password)` — hash
   server-side via `crypt(..., gen_salt('bf'))`, gated by
   `EXISTS (SELECT 1 FROM admin_users WHERE id = auth.uid())` (mirrors how
   `AuthGuard.jsx` already gates the admin panel itself — `admin_users.id`
   IS the Supabase Auth user id). Granted to `authenticated` only, never
   `anon`. Both also `INSERT` into their respective alerts table on
   success, so the reset itself produces the notice — one write, no
   separate notification step needed.

### Admin panel
- `studentService.js`/`employeeService.js`: `resetStudentPassword()`/

### Mobile (student popup)
- `supabase_service.dart`: `fetchStudentAlerts(studentId)`, identical shape
  to the existing `fetchTeacherAlerts`.
- `student_home.dart`'s `_loadNotifications()`: added
  `...alerts.map(alertAsNoticeItem)` into the `combined` feed — reused the
  existing generic adapter as-is (it only reads `id`/`title`/`message`/
  `created_at`, no teacher-specific logic), zero new adapter code needed.
  This is the exact same pattern `teacher_home.dart` already used for
  `teacher_alerts` — gets the on-open popup behavior for free via the
  pre-existing `shouldShowNoticePopupToday` mechanism.
