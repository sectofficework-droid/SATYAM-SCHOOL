## Issue 4 — IST timezone bug in the date arrows (root cause + app-wide sweep)
**Symptom reported:** "but when i go back clciking on right not working."
**Root cause:** `shiftStaffDate()` and the "today" default both built the
`YYYY-MM-DD` string via `d.toISOString().slice(0,10)`. `toISOString()`
converts to UTC first; a `Date` built from a local-midnight `"...T00:00:00"`
string, for any **positive** UTC offset (IST = UTC+5:30), rolls back onto the
*previous* UTC calendar day once converted. Concretely: going back one day from
today actually went back two; going forward one day from that spot landed back
on the same date (computed twice, canceling out) instead of advancing.
**Fix:** `toIsoDateLocal(d)` — reads `d.getFullYear()/getMonth()/getDate()`
directly, no UTC conversion. Applied to `shiftStaffDate`'s `today`/`next`
values and the staffAttendance default-date computation.
**Sweep ("fix wherer needed" → "fix"):** grepped the whole
`toISOString().slice(0,` pattern repo-wide (19 files hit). Fixed the pattern
everywhere it computed an actual local "today"/"this month" value — **16
files**, listed in `LOG-2026-10-01.md` Session 2. Individually traced and
**deliberately left unfixed** (same-class pattern, but already correct via a
different technique — do not "fix" these if re-encountered):
- `admin-panel/src/app/(dashboard)/dashboard/page.js:203` and
  `admin-panel/src/lib/sefFeesService.js:36` — both add a hardcoded `+5.5h`
  (`IST_OFFSET_MS`) to `Date.now()` *before* the UTC slice, which correctly
  yields the IST calendar month regardless of the viewer's own browser
  timezone (deliberate — not viewer-local, always school's own IST).
  `sefFeesService.js`'s is itself a prior fix, REQ-BUG-043.
- `admin-panel/src/lib/staffLeaveService.js:38` (`dateRange()`) — builds the
  whole range with `Date.UTC(...)`/`cursor.setUTCDate(...)` throughout, so it
  never mixes local and UTC at all; its own comment already explains why.
- `admin-panel/src/components/DateInputDMY.jsx:24` (`dmyDigitsToIso`'s
  round-trip validity check) — both the parse (`new Date(iso)` on a date-only
  string, which the JS spec parses as UTC) and the re-slice are UTC-to-UTC;
  no local time ever enters.
- `admin-panel/src/app/(dashboard)/super-admin/page.js:1695`
  (`SalaryPanel.loadPayments`'s `p_to` boundary) — `new Date(m + "-01")` is a
  date-only (UTC) parse, so it's UTC midnight regardless of browser timezone;
  `.setMonth()` preserves local wall-clock time (which for a UTC-midnight
  instant under IST is 05:30 local), and converting back to UTC after
  incrementing the month lands exactly on the next month's UTC midnight again
  — the two conversions cancel out symmetrically for a fixed, DST-free
  offset. Verified by hand before leaving it.
**New shared helper:** `toIsoDateLocal` moved to `admin-panel/src/lib/utils.js`
(exported alongside the existing `cn`/`fmtDMY`); `report/page.js`'s local copy
removed in favor of `import { toIsoDateLocal } from "@/lib/utils"`.
**Verification:** `eslint` clean on every touched file. Not browser-clicked
(no live browser session this session) — logic traced by hand for each
"left alone" case rather than assumed safe.

## Issue 5 — Staff Attendance delete "not working" → real root cause, 3 absence-marking paths, a leftover security gap
**Symptom reported:** delete action in the report appears not to work.
**Investigation order:** read `delete/route.js` and its RPC fallback — looked
correct. Confirmed `SUPABASE_SERVICE_ROLE_KEY` is set in Vercel
(`filter_project_envs`, names only, never decrypted). **Live-tested all 3
delete code paths directly against production** rather than trusting the code
read: inserted disposable test `employee_attendance` rows via Supabase
(`1999-01-01`/`1999-01-02`, real employee id, no FK issues), called
`https://satyam-stars-international-school-a-six.vercel.app/api/staff-attendance/delete`
via `curl` for (a) single `employeeId+date`, (b) `items[]` bulk, (c)
`employeeId+dates[]` (rollup single-row delete), verified each left zero rows
behind via a follow-up `SELECT`. **All three genuinely delete** — the API
itself was never broken.

**Root cause:** `getStaffAttendanceForReport()` (`reportService.js`) POSTs to
`/api/staff-attendance/sync-absent` on every call — i.e. every report load.
That route auto-inserts `status='A'` for today for any active employee with no
row yet, once `kiosk_settings.absent_cutoff_time` has passed. Deleting today's
auto-marked row is real, but the next report refresh calls `sync-absent`
again, sees the employee "missing" once more, and silently reinserts it.
**Policy decision (AskUserQuestion, confirmed):** a delete should stick for
the rest of the day.

**Fix 1 — exclusions table.** New
`employee_attendance_sync_exclusions(employee_id uuid, date date, created_at,
PRIMARY KEY(employee_id, date))`, RLS enabled with **zero policies** (nothing
but the service-role server should ever touch it — no client grants, by
design, not an oversight). `delete/route.js`'s `recordTodayExclusions()`
upserts into it after every one of its delete cases (1a/1b/Case2/Case3/Case4),
filtered to pairs whose date matches `todayIST()` — past-date deletes record
nothing, since `sync-absent` never touches past dates anyway.
`sync-absent/route.js` now also selects from this table and excludes those
`employee_id`s from `missingEmps`. `admin_delete_staff_attendance` (the RPC
fallback used only when `SUPABASE_SERVICE_ROLE_KEY` is absent) got the same
upsert logic added in all 4 of its branches.

**Fix 2 — found live-testing Fix 1.** Restoring a deleted real "Absent" test
row (employee `06dd2e7c-e368-4366-9251-246d2b2aeb85`, `2026-10-01`) hit a
unique-constraint conflict: a new row had appeared 18s after the exclusion was
recorded, same employee/date, different `id`. `sync-absent` itself had
returned `marked: 0` moments earlier (correctly respecting the exclusion), so
something else was marking it. Found it: `auto_mark_absent_staff` has **two
overloads** — `(p_date, p_secret)` (secret-checked, called by the daily
Vercel cron, `/api/cron/mark-staff-absent`) and a **bare `(p_date)` with no
auth check at all**, confirmed via `has_function_privilege(role, oid,
'EXECUTE')` still granted to `anon`/`authenticated`. Repo-wide grep
(`mobile-app/lib` + `admin-panel/src`) found zero callers of the 1-arg form —
only the cron calls the secured 2-arg one. This is REQ-SEC-010 item 2
(`TODO.md`), found 2026-09-19: that fix *added* the secured overload but,
since Postgres allows overloading by signature, never dropped the original —
left it coexisting and still live. Patched **both** overloads to add
`AND NOT EXISTS (SELECT 1 FROM employee_attendance_sync_exclusions x WHERE
x.employee_id = e.id AND x.date = p_date)` to their insert's `WHERE NOT
EXISTS` guard.

**Verification (live, twice, on real rows — not synthetic):** captured a real
"Absent" row's exact field values before each test; deleted via the live API;
confirmed the exclusion row exists; called `sync-absent` directly (→
`marked: 0`) **and** called `auto_mark_absent_staff('2026-10-01'::date)`
directly via Supabase (→ `0`) to prove the RPC-level fix too; confirmed via
`SELECT` the row stayed gone through both; restored the original row's
content (same employee/date/status; second test used a fresh insert since the
restore conflict in test 1 meant the original `id` was already taken);
deleted the test's own exclusion row afterward. **Left untouched:** one
exclusion row found during cleanup that wasn't from this session's testing —
employee "Play Store Reviewer" (`29200638-0477-4cda-b411-d85883c36f57`),
created during the test window — a real, concurrent delete by the actual user
on a different employee; confirmed their attendance row is still correctly
absent-not-reinserted and left the exclusion in place rather than removing
protection from a live user action.

**Fix 3 — closing the gap for real, user confirmed "yes".** Checked no
DB-internal dependents (`pg_depend` query, cross-referencing `pg_proc` for
both signatures) and re-confirmed the repo-wide grep result before dropping.
`DROP FUNCTION IF EXISTS public.auto_mark_absent_staff(date);` — applied
live. Only `auto_mark_absent_staff(p_date date, p_secret text)` remains
(`pg_proc` confirmed post-drop). Updated `TODO.md`'s existing REQ-SEC-010
item-2 entry with a dated closure note (don't re-file this as a new finding —
it's the same one, now actually finished) rather than opening a new REQ-SEC
number.
